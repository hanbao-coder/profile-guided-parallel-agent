# 研究过程记录（内部）

本文件是项目开发过程的可追溯记录，不是对导师的汇报材料。每一项只记录已经由
代码、测试或实验数据证实的事实；后续制作汇报时可从这里提取问题、判断和边界。

## R1：不能把“生成了 Ray 语法”当成并行成功

**观察。** 朴素策略把每个输入项提交为一个 Ray Task。在 Tiny Tasks 的三轮 WSL2
正式实验中，M1 的预热后平均加速仅 0.286x，2000 个细粒度任务的调度成本超过了
计算收益。

**处理。** 系统先测空任务开销和样本任务耗时，再选择 Worker/Chunk；若预测收益
不足则回退串行。

**证据。** 优化策略把 Tiny Tasks 的任务数降至平均约 10.7 个，预热后平均加速
为 3.165x，且输出与串行黄金结果一致。

**可解释点。** 性能反馈的价值不是让模型“更会写代码”，而是使系统可以拒绝成本
高于收益的并行计划。

## R2：平均耗时不足以描述负载不均衡

**观察。** Load Imbalance 的前 1/4 个输入项远重于其余项。旧版优化器只用平均
单项耗时，选择 4 个大块；三轮正式实验中该策略的平均加速只有 1.086x，而每项一个
任务的朴素策略达到 2.703x。

**定位。** 4 个连续大块会把重任务集中到少数 Worker。这里的瓶颈不是 Ray 调度
开销，而是静态划分产生的尾部拖延（straggler）。

**处理。** 改为在输入的不同位置进行分层抽样，估计单项耗时的变异系数；变异高时，
预测模型为少量 Chunk 加入失衡惩罚，促使优化器保留更多任务供 Ray 动态分发。

**证据。** 新版选择 32 个 Chunk。三轮正式复测中，Load Imbalance 的 M2 平均加速
为 3.027x，超过 M1 的 2.703x；所有结果正确。

**边界。** 这是基于分层样本的启发式，不是完整的运行时调度器；对于任务耗时随输入
动态变化且样本不具代表性的程序，仍需要在线重平衡或更保守的候选搜索。

## R3：首次运行与预热运行必须分开报告

**观察。** WSL2 单节点 Ray 的初始化平均约 3.126 秒，而预热空任务开销约
0.230 毫秒/任务。把初始化费用计入首次执行后，所有并行观察都慢于串行。

**处理。** 运行器分别保存预热后运行时间、首次使用总时间和对应加速比，并计算
启动成本摊销所需的运行次数。

**可解释点。** 一次性脚本不应仅凭预热加速宣称适合 Ray；重复批处理或常驻服务才
可能摊销启动成本。

## R4：Windows 环境问题不应被掩盖

**观察。** 当前 Windows 中文主机名使本机 Ray 2.56.1 运行时不稳定；GitHub Linux
早期还因长工作目录触发 AF_UNIX Socket 路径超过 107 字节的限制。

**处理。** 日常开发保留 multiprocessing 后端；真实 Ray 运行转到 WSL2 Ubuntu，
并将 Ray 临时目录固定在短路径 `/tmp/pa_ray`。

**证据。** WSL2 的三轮正式实验全部正确；GitHub Actions 的 Linux Ray 冒烟测试
已通过。

**可解释点。** “环境兼容性”本身是分布式系统工程的一部分。问题被定位、复现、
修复并加入回归检查，比在不兼容环境中强行得到一次结果更可靠。

## R5：资源指标需要和墙钟时间一起解释

**观察。** 初始 CPU 采样会把新出现子进程的累计 CPU 时间误算到当前间隔，短任务
出现异常尖峰。

**处理。** 监视器改为逐 PID 保存 CPU 基线，在结束时补一次样本；并行模式才统计
子进程。

**边界。** CPU 百分比以一个逻辑核心为 100%，并包括 Ray 的相关进程；它只能辅助
说明并发是否发生，不能替代耗时、任务数和正确性。

## R6：Agent 主流程与性能运行器必须使用同一执行语义

**观察。** 统一性能运行器已经支持真实 Ray，但早期模板 Agent 生成的候选程序
只使用 `ProcessPoolExecutor`。这会造成“Agent 能生成什么”和“性能实验测量什么”
不完全一致的风险。

**处理。** 模板候选新增可选 `--backend ray`，Agent 管道把该选择传递到候选执行器；
受控 LLM 代码生成继续保留 ProcessPool 沙箱，并在请求 Ray 时明确拒绝，避免绕开
AST 安全约束。结构化 `parallel_plan.json` 与 JSON Schema 也同步加入 Ray 后端，
避免计划字段仍写 multiprocessing、实际候选却执行 Ray 的语义不一致。

**证据。** 在 WSL2 中以 Prime Count 运行 DeepSeek Agent：模型分析与规划、候选
生成、串行黄金运行和真实 Ray Task 运行均完成，结果 `3491` 一致，任务数为 2。

**边界。** Agent 候选由独立子进程执行，每次 Ray 调用会重新初始化运行时；这条
路径目前用于端到端功能和正确性验证。性能结论仍使用已预热、统一进程内的 Ray
运行器，不能把二者混为一谈。

## R7：加速比不能完整表达并行成本

**观察。** 初版结果包含运行时间、CPU、加速比与并行效率，但没有直接保存标准
并行总开销 \(O_p=pT_p-T_1\)。仅看加速比不容易区分“确实节省计算资源”和
“使用更多核心换取少量墙钟时间”的情况。

**处理。** 运行器新增 `parallel_overhead_core_seconds` 和归一化
`parallel_overhead_ratio`，并分别记录预热后与首次使用值。正式 Ray 旧数据可由
已保存的 Worker 数与加速比精确恢复，因此没有为增加派生指标重复运行实验。

**证据。** 在方差感知正式实验中，Load Imbalance 的 M2 预热归一化开销约
0.322，低于 M1 的 0.487；Tiny Tasks 的 M1 约为 12.993，而 M2 约为 0.268。
首次使用开销仍极高，与 Ray 初始化成本结论一致。

## R8：阶段性验收不能代替最终研究验收

**观察。** 早期发布脚本能够验证 multiprocessing 配置消融、任务融合和 DAG
模型，但它并不知道后续增加的真实 Ray 数据、方差感知改进和 Agent–Ray 契约。
继续使用旧验收得到绿灯，只能证明旧范围没有损坏。

**处理。** 新增独立的研究核心验收，逐轮检查两组 Ray 数据的 3×8×3 方法矩阵、
24 份原始报告、360 次正式计时、全部正确、前后版本改善和并行开销字段；同时
检查 Agent 候选模板确实包含 Ray Task 路径。该验收不调用 DeepSeek。

**证据。** 本地完整验收和自动化测试通过；相同命令已接入 GitHub Linux 工作流。

## R9：连接到集群不等于任务真的跨节点执行

**观察。** 单机启动的 Ray Head 和真实多节点集群都可以通过同一个
`ray.init(address=...)` 接口连接。如果结果只保存“连接成功”，就可能把单机 Head
误写成多节点实验；即使集群中有多个节点，也不能证明任务实际被调度到了多个节点。

**处理。** 运行器新增 `--ray-address`，同时保存存活节点、不同物理地址、CPU/GPU
资源，并让每个 Ray Task 返回实际执行节点 ID。结果分别记录“集群是否包含多个
物理节点”和“任务是否实际跨多个节点执行”，两者不能互相替代。动态加载的工作负载
不再作为整个模块闭包发送，而是显式序列化 `unit` 函数，降低远端节点依赖本地源码
路径的风险。

**证据。** 当前代码分别通过了本地自动启动 Ray 和连接预先启动 Head 的真实运行；
两次结果都正确地记录为 1 个物理节点、1 个实际执行节点、非多节点。更换任务
序列化方式后，又对 8 类工作负载完成小规模 M0/M1/M2 冒烟，24 个方法结果全部
正确且都记录了实际执行节点。该测试只证明集群连接、函数传输和审计路径可用，
不作为多节点加速证据。

**边界。** 真正的多节点结论仍需至少两台互通的 Linux 机器，并要求
`executed_on_multiple_nodes=true`；之后还要在相同实验协议下比较单节点与多节点
耗时，不能仅凭节点数量宣称扩展性。

## R10：可审计性不应以原始数据无限膨胀为代价

**观察。** 第一版节点审计为每个 Ray Task 保存一次节点 ID。Tiny Tasks 的朴素
策略每轮会产生 2000 个任务，导致相同节点 ID 在 JSON 中重复数千次；一组 33 文件
的正式数据因此从约 0.5 MB 膨胀到约 2.9 MB。

**定位。** 研究真正需要的是“每个节点执行了多少任务”和“是否跨节点”，而不是
保留一条没有额外信息的重复字符串。逐任务列表的空间复杂度随任务数线性增长，
还会增加 Git、解析和长期归档成本。

**处理。** 将逐任务 ID 列表压缩为 `execution_node_counts` 计数字典。每次运行要求
节点计数之和等于 `task_count`，报告级计数必须能由全部原始运行重新聚合；CI 的
Ray 冒烟和正式数据验收都会检查这两个不变量。

**证据。** 压缩后的 v0.21 正式数据为 33 个文件、约 0.49 MB；3 轮、8 类任务、
M0/M1/M2、每方法 5 次，共 360 次正式计时全部正确。M2 预热宏平均加速为
2.406x，退化率 0%，相对 M1 的几何平均提升为 1.734x，胜率 87.5%。

## R11：前端已经证明的语义不能在 Agent 阶段丢失

**观察。** 首版普通循环前端能够把 `run_serial` 中的“逐项处理→收集→聚合”
转换成标准工作负载包装器，离线 Agent 也能正确执行。但 DeepSeek 第一次只看到
生成后的包装器，认为 `unit` 委托给外部模块、无法确认副作用，因此拒绝并行。
模型的判断对孤立包装器是合理的，却丢失了前端已经检查过的原始循环语义。

**处理。** 标准化元数据同时保存原始源码 SHA-256、包装器 SHA-256、入口函数、
逐项函数和聚合函数映射。Agent 分析前重新运行确定性模式匹配并验证两个哈希；
DeepSeek Pro 改为审查原始串行源码和前端证据，而生成代码仍绑定标准包装器。
若源码、包装器或元数据任一发生变化，流程立即拒绝。

**证据。** 修复后的真实 WSL2 流程使用 DeepSeek V4 Pro 分析、V4 Flash 规划，
共 2 次调用、2435 Token；最终计划绑定 Ray 后端，串行与 Ray 结果均为 `3491`，
任务数为 2，正确性门通过。单命令 `agent-loop` 又分别在 Windows
multiprocessing 和 WSL2 Ray 环境通过。

**边界。** 目前只识别一个严格的三段式循环模式，不支持任意循环重构。小输入的
Agent 候选每次在独立子进程初始化 Ray，端到端性能很差；这条链路用于证明输入
转换和正确性，性能结论仍来自统一、预热的正式运行器。Agent 候选跨节点执行还
要求各节点可见相同源码路径，尚未加入自动运行时环境打包。

## R12：多个阶段绿灯不能自动等价为整个项目绿灯

**观察。** 仓库长期保留了第一阶段验收和当前研究核心验收。前者覆盖配置消融、
任务融合、DAG 调度和早期交付边界，后者覆盖真实 Ray、方差感知、Agent–Ray
契约和普通循环前端。只运行其中一个，都不能证明完整项目仍然一致。

**处理。** 新增统一 `verify_project.py`，顺序执行历史证据门和当前研究核心门，
完整测试只运行一次，并可选接收真实 Ray 冒烟 JSON。GitHub 的主分支、标签和
Pull Request 全部改用同一项目级入口。

**发现与修复。** 第一次统一验收中，74 项功能测试通过，唯一失败项是 CI 回归
测试仍硬编码旧验收命令。这证明发布流程本身也需要版本同步。更新测试契约后，
统一验收完整通过。

**证据。** 当前项目级命令同时恢复并检查：完整配置方法 1.149x、固定配置退化率
70.8%→0%、单消费者任务融合 22.02x、两类 DAG 模型改善、当前 Ray M2 2.406x、
M2/M1 几何平均 1.734x、普通循环前端与 76 项测试；全程不读取 DeepSeek Key。
