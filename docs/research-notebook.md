# 研究过程记录（内部）

本文件是项目开发过程的可追溯记录，不是对导师的汇报材料。每一项只记录已经由
代码、测试或实验数据证实的事实；后续制作汇报时可从这里提取问题、判断和边界。

## R1：不能把“生成了 Ray 语法”当成并行成功

**观察。** 朴素策略把每个输入项提交为一个 Ray Task。在 Tiny Tasks 的三轮 WSL2
正式实验中，M1 的预热后平均加速仅 0.286x，2000 个细粒度任务的调度成本超过了
计算收益。

**处理。** 系统先测空任务开销和样本任务耗时，再选择 Worker/Chunk；若预测收益
不足则回退串行。

**证据。** 优化策略把 Tiny Tasks 的任务数降至平均约 10.7 个，预热后平均加速
为 3.165x，且输出与串行黄金结果一致。

**可解释点。** 性能反馈的价值不是让模型“更会写代码”，而是使系统可以拒绝成本
高于收益的并行计划。

## R2：平均耗时不足以描述负载不均衡

**观察。** Load Imbalance 的前 1/4 个输入项远重于其余项。旧版优化器只用平均
单项耗时，选择 4 个大块；三轮正式实验中该策略的平均加速只有 1.086x，而每项一个
任务的朴素策略达到 2.703x。

**定位。** 4 个连续大块会把重任务集中到少数 Worker。这里的瓶颈不是 Ray 调度
开销，而是静态划分产生的尾部拖延（straggler）。

**处理。** 改为在输入的不同位置进行分层抽样，估计单项耗时的变异系数；变异高时，
预测模型为少量 Chunk 加入失衡惩罚，促使优化器保留更多任务供 Ray 动态分发。

**证据。** 新版选择 32 个 Chunk。三轮正式复测中，Load Imbalance 的 M2 平均加速
为 3.027x，超过 M1 的 2.703x；所有结果正确。

**边界。** 这是基于分层样本的启发式，不是完整的运行时调度器；对于任务耗时随输入
动态变化且样本不具代表性的程序，仍需要在线重平衡或更保守的候选搜索。

## R3：首次运行与预热运行必须分开报告

**观察。** WSL2 单节点 Ray 的初始化平均约 3.126 秒，而预热空任务开销约
0.230 毫秒/任务。把初始化费用计入首次执行后，所有并行观察都慢于串行。

**处理。** 运行器分别保存预热后运行时间、首次使用总时间和对应加速比，并计算
启动成本摊销所需的运行次数。

**可解释点。** 一次性脚本不应仅凭预热加速宣称适合 Ray；重复批处理或常驻服务才
可能摊销启动成本。

## R4：Windows 环境问题不应被掩盖

**观察。** 当前 Windows 中文主机名使本机 Ray 2.56.1 运行时不稳定；GitHub Linux
早期还因长工作目录触发 AF_UNIX Socket 路径超过 107 字节的限制。

**处理。** 日常开发保留 multiprocessing 后端；真实 Ray 运行转到 WSL2 Ubuntu，
并将 Ray 临时目录固定在短路径 `/tmp/pa_ray`。

**证据。** WSL2 的三轮正式实验全部正确；GitHub Actions 的 Linux Ray 冒烟测试
已通过。

**可解释点。** “环境兼容性”本身是分布式系统工程的一部分。问题被定位、复现、
修复并加入回归检查，比在不兼容环境中强行得到一次结果更可靠。

## R5：资源指标需要和墙钟时间一起解释

**观察。** 初始 CPU 采样会把新出现子进程的累计 CPU 时间误算到当前间隔，短任务
出现异常尖峰。

**处理。** 监视器改为逐 PID 保存 CPU 基线，在结束时补一次样本；并行模式才统计
子进程。

**边界。** CPU 百分比以一个逻辑核心为 100%，并包括 Ray 的相关进程；它只能辅助
说明并发是否发生，不能替代耗时、任务数和正确性。

## R6：Agent 主流程与性能运行器必须使用同一执行语义

**观察。** 统一性能运行器已经支持真实 Ray，但早期模板 Agent 生成的候选程序
只使用 `ProcessPoolExecutor`。这会造成“Agent 能生成什么”和“性能实验测量什么”
不完全一致的风险。

**处理。** 模板候选新增可选 `--backend ray`，Agent 管道把该选择传递到候选执行器；
受控 LLM 代码生成继续保留 ProcessPool 沙箱，并在请求 Ray 时明确拒绝，避免绕开
AST 安全约束。结构化 `parallel_plan.json` 与 JSON Schema 也同步加入 Ray 后端，
避免计划字段仍写 multiprocessing、实际候选却执行 Ray 的语义不一致。

**证据。** 在 WSL2 中以 Prime Count 运行 DeepSeek Agent：模型分析与规划、候选
生成、串行黄金运行和真实 Ray Task 运行均完成，结果 `3491` 一致，任务数为 2。

**边界。** Agent 候选由独立子进程执行，每次 Ray 调用会重新初始化运行时；这条
路径目前用于端到端功能和正确性验证。性能结论仍使用已预热、统一进程内的 Ray
运行器，不能把二者混为一谈。

## R7：加速比不能完整表达并行成本

**观察。** 初版结果包含运行时间、CPU、加速比与并行效率，但没有直接保存标准
并行总开销 \(O_p=pT_p-T_1\)。仅看加速比不容易区分“确实节省计算资源”和
“使用更多核心换取少量墙钟时间”的情况。

**处理。** 运行器新增 `parallel_overhead_core_seconds` 和归一化
`parallel_overhead_ratio`，并分别记录预热后与首次使用值。正式 Ray 旧数据可由
已保存的 Worker 数与加速比精确恢复，因此没有为增加派生指标重复运行实验。

**证据。** 在方差感知正式实验中，Load Imbalance 的 M2 预热归一化开销约
0.322，低于 M1 的 0.487；Tiny Tasks 的 M1 约为 12.993，而 M2 约为 0.268。
首次使用开销仍极高，与 Ray 初始化成本结论一致。

## R8：阶段性验收不能代替最终研究验收

**观察。** 早期发布脚本能够验证 multiprocessing 配置消融、任务融合和 DAG
模型，但它并不知道后续增加的真实 Ray 数据、方差感知改进和 Agent–Ray 契约。
继续使用旧验收得到绿灯，只能证明旧范围没有损坏。

**处理。** 新增独立的研究核心验收，逐轮检查两组 Ray 数据的 3×8×3 方法矩阵、
24 份原始报告、360 次正式计时、全部正确、前后版本改善和并行开销字段；同时
检查 Agent 候选模板确实包含 Ray Task 路径。该验收不调用 DeepSeek。

**证据。** 本地完整验收和 65 项测试通过；相同命令已接入 GitHub Linux 工作流。
