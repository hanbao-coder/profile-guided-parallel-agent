# Radon 人工参考并行版本复核

## 目的

人工参考版本不是 Agent 的最终方法，而是用来回答一个前提问题：如果已经知道怎样避开进程间
状态传递问题，Radon 这项固定工作负载是否真的能得到端到端加速？只有答案为“是”，才适合把
这种写法当作 Agent 后续学习的性能参考。

## 参考修改

参考补丁把文件分析函数移到模块顶层。子进程只接收文件名和少量布尔配置，排序和汇总仍留在
主进程，从而避免把整个 `Harvester` 对象和动态配置传给 Windows 子进程。补丁保存在
`docs/data/radon-manual-reference.patch`。

## 固定协议复核结果

2026-08-08 使用从固定提交重新建立的干净 Radon 副本复核：

- 原项目测试：399 项通过，5 项按项目设置跳过；
- 正确性：B0 与 B3 的 5 次正式运行输出哈希全部相同；
- B0 串行中位耗时：12.7008 秒；
- B3 人工参考中位耗时：12.7182 秒；
- 加速比：0.9986 倍；
- 预先规定的有效门槛：1.05 倍；
- 结论：修改在语义上正确，但不是有效性能上界。

完整机器可读结果见 `docs/data/radon-manual-reference-summary.json`，复核入口为

## 对旧结论的更正

早期记录曾报告约 5.98 倍加速，但该数字来自旧测量记录，未能在当前固定源码、路径无关输出、
相同输入和配对计时协议下复现。因此本项目撤回“Radon 存在 5.98 倍人工上界”的说法，也不再
用它证明 Agent 只要找到 Worker 边界就一定能加速。

旧环境回放还观察到 Windows 进程启动时间波动较大，但现有证据不足以把旧数字与新数字的差异
归因于某一个因素。可确认的只有：在当前可复现协议下，B3 与 B0 基本持平。

## 研究含义

这次复核区分了两个原本混在一起的问题：

1. 把复杂对象移出 Worker 边界，确实能避免一类序列化和状态错误；
2. 避免错误并不自动等于获得端到端收益。

因此 Worker 边界检查仍可作为正确性诊断工具，但不能仅凭这一条规则预测性能，也不应继续把
Radon 作为该规则的加速成功样本。
