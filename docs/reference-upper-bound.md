# 人工参考并行版本：Radon

## 目的

这项实验不是把人工方案当作 Agent 的最终方法，而是回答两个更基础的问题：

1. Radon 的固定工作负载是否真的存在可获得的端到端并行收益；
2. 初步 Agent 方案失败后，怎样修改并行边界才能同时通过测试、保持输出并获得加速。

如果人工方案也无法加速，就不能把 Agent 的失败简单归因于代码理解能力。

## 第一次方案为什么失败

初步 Agent 方案直接把绑定方法 `self._analyze_file` 提交给进程池。这个方法会连同
`Harvester` 对象和动态 `Config` 一起传给 Windows 子进程，反序列化时触发递归错误。
项目又把子进程异常包装成普通的 `{error: ...}` 输出，因此程序表面上正常结束且耗时很短，
但 2 项测试失败，规范化输出也与串行基线不同。

随后人工参考方案把文件分析函数移到模块顶层，只给子进程传入文件名和少量布尔配置。
第一次修改仍失败，因为排序配置实际上是一个 `lambda`，同样不能跨进程传递。

## 正确的参考方案

最终方案把职责拆成两部分：

- 子进程只读取单个文件并计算复杂度，返回原始分析结果；
- 主进程按照原项目的排序函数整理结果，并保持文件顺序不变。

这样既没有传递整个 `Harvester`，也没有传递不可序列化的排序函数。对于少于 8 个文件或
标准输入的情况，继续使用原串行路径，避免改变小输入行为。

## 验证结果

- 项目测试：399 项通过，5 项按原项目设置跳过；
- 正确性：5 次正式运行的规范化输出哈希均为
  `4c4dbb169bc6e13d5a66052bb77d1f779aca90ea93dd00e97b2d07d05375d3df`，
  与串行基线完全相同；
- 串行中位耗时：13.4017 秒；
- 人工参考并行版中位耗时：2.2397 秒；
- 有效加速比：约 5.98 倍；
- 测量方式：1800 个固定 Python 文件，预热 1 次，正式运行 5 次。

原始计时和规范化输出保存在
`results/reference/radon-state-minimal.json`。

## 当前能说明什么

这项实验说明 Radon 本身具有真实的并行空间，也说明“并行边界传递哪些状态”会同时影响
可运行性、正确性和性能。但它目前只来自一个项目，不能据此直接确定最终研究观点。
下一步仍需观察 Vulture 和 Chardet 的独立 Agent 运行，判断同类问题是否跨项目重复出现，
以及是否存在影响更大的其他失败类型。
