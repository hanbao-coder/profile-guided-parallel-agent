# 第一次导师汇报口头提纲

建议总时长：8～10 分钟。

## 0:00–1:00：一句话说明项目

老师好，我把题目缩小为“基于性能剖析与依赖分析的 Python 自动并行化
Agent”。我的重点不是让模型简单生成并行语法，而是分析依赖、任务粒度和
通信开销，并通过真实运行数据决定是否并行以及如何并行。

## 1:00–2:00：为什么要这样做

初步实验发现，LLM 或规则生成的并行代码即使结果正确，也可能明显更慢。
主要原因是 Worker 启动、任务调度、输入输出序列化以及任务粒度太小。因此
我把“性能退化率”和“端到端加速”作为核心指标。

## 2:00–4:00：系统怎么工作

按顺序讲：

1. AST 分析依赖和支持范围；
2. Agent 输出结构化分析和并行计划；
3. 生成候选程序；
4. 串行和并行分别运行；
5. 验证结果；
6. 测量冷启动、热运行和通信代理；
7. 搜索 Worker/Chunk；
8. 无收益时回退串行。

不要逐个讲代码文件。

## 4:00–6:00：讲两个最有代表性的结果

### Prime Count

计算占主导。五次重复实验中热运行约 3.18 倍，计入 Worker 启动后约
1.92 倍。说明并行
确实有效，但必须区分热运行和端到端时间。

### Tiny Tasks

朴素并行创建大量任务，端到端只有约 0.29 倍加速，也就是明显比串行慢；
M2识别收益不足并回退。说明系统的
价值不仅是“加速”，还包括“避免有害并行”。

随后用一句话补充 Word Count 和 Pairwise Distance 的 MB 级输入序列化。

再补充性能反馈消融：Tiny Tasks 的一次性生成和正确性反馈虽然输出正确，
但都只达到约 0.45 倍加速；性能反馈组根据三次实测回退串行，恢复到 1.00
倍基线。Prime Count 则测得约 1.78 倍并保留并行，说明 Gate 不是一律拒绝。

正式实验进一步覆盖 4 个任务、3 种模式、3 次独立模型运行，共 36 个作业。
三组正确率都是 100%，但一次性和正确性反馈的性能退化率都是 50%；性能
反馈组为 0%，宏平均有效加速从约 1.08 倍提高到 1.27 倍。这里的主要贡献
不是夸大单个任务加速，而是避免生成“正确但更慢”的代码。

最后补充生成器正式实验：模板和 LLM 共享同一份分析与并行计划，覆盖 4 个任务、
每个任务 3 次独立生成。模板 12/12 正确，LLM 11/12 正确，并发生 8 次代码
修复。LLM 的表面宏平均运行比约 1.021 倍，但保守比较只有 3/11 占优，不能
宣称稳定加速。这个结果说明确定性代码骨架应保留，Agent 应主要负责收益判断和
性能决策。

在此基础上，我完成了 8 个任务、24 个独立作业的多尺度配置搜索。固定
4 Worker / 4 Chunk 的性能退化率为 62.5%，自适应选择为 0%；宏平均有效
加速从 0.965 倍提高到 1.186 倍。负载不均衡任务相对固定配置提高 1.315 倍，
大载荷轻计算任务通过拒绝并行提高 2.231 倍。这里严格分离了小样本调参、
完整规模确认和独立留出评测，避免把调参结果直接当作最终结论。

目前已经把该搜索接入 DeepSeek Agent：模型负责分析，确定性工具负责参数决策。
一次真实负载不均衡任务中选择 4 Worker / 8 Chunk，最终独立验证加速 1.117 倍
且输出正确；两次模型调用共 2,115 tokens。

消融实验进一步比较固定配置、小样本直接决策和完整三阶段方法。固定配置宏平均
只有 0.926 倍，退化率 70.8%；小样本方法没有退化，但 24 次全部选择串行；
完整方法在保持 0% 退化率的同时恢复 7 次有收益并行，宏平均达到 1.149 倍。
这说明完整规模确认能够纠正小样本的过度保守。

通信感知融合实验又验证了融合不能盲目进行。大中间数据单消费者链融合后消除
约 8 MiB 传输并减少一半任务，热运行达到约 22 倍；但在重生产者双分支中，
固定逐边融合重复计算生产阶段，只有 0.545 倍。感知策略识别结果复用并拒绝
融合，从而避免退化。这里报告的是共享预热进程池下的融合净影响。

进阶部分还实现了简化 DAG 调度模型。关键路径优先在计算关键图上把 makespan
从 2.18 降到 1.85，在通信关键图上从 0.98 降到 0.78；两图 Worker 空闲比例
都降到约 24%。这部分是确定性调度模型，不作为真实 Ray 加速结果。

## 老师可能追问

### 为什么选择 multiprocessing 而不是直接 Ray？

方法层和执行层已经分开。当前机器中文主机名触发 Ray Windows 运行时错误，
所以先用相同的多进程任务语义验证算法；最终会在兼容 Linux 环境补 Ray。

### Agent 和普通脚本有什么区别？

普通脚本使用固定规则。Agent会读取代码分析、执行错误、正确性结果和性能
数据，生成结构化计划与并行实现并迭代修改。当前 DeepSeek 已覆盖正确候选、
依赖拒绝、正确但性能退化，以及代码安全拒绝后自动修复。

### 为什么并行效率会偶尔超过 1？

这是短时实验的测量波动，不是突破理论上限。正式实验会增加重复次数并报告
中位数和四分位距。

### 为什么不直接做任意 Python 代码？

20 天内做任意代码不现实。先在明确范围内把正确性、性能和反馈闭环做扎实，
再逐步放宽；ParEval-Repo也说明跨文件和构建系统会显著提高难度。

### 当前最像创新点的部分是什么？

实测开销驱动的收益 Gate、自适应 Worker/Chunk，以及把“性能退化率”作为
核心指标，目标是避免模型为了并行而并行。
