# M8 研究问题与实验预注册：让 Agent 先看清 Worker 边界

## 1. 为什么重新确定问题

早期版本把依赖检查、性能反馈、Chunk 搜索、回退等功能都接进了系统，但老师指出，
这仍容易变成“功能越做越多”，而不是围绕一个现象提出并验证观点。因此 M8 不再把
所有模块都写成贡献，而是从已经完成的真实项目实验中重新找问题。

我逐个复核了 Chardet、MkDocs、Radon 和 Vulture 中 30 次实际候选修改。只有 1 次
同时通过项目测试、输出检查和性能检查。其余 29 次中，有 16 次的主要问题与 Worker
边界有关，占 55.2%。这里的“边界”是指主程序把什么数据、对象或状态交给线程/进程，
以及多个 Worker 之间共享什么。

典型现象包括：

- Chardet：父进程中动态替换的函数没有进入子进程，原有 CLI 行为发生变化；
- Radon：配置中包含 lambda，整个配置传给子进程后无法序列化；
- MkDocs：页面构建依赖共享配置、插件和渲染环境，并行后输出发生变化；
- Radon：代码虽然正确，但进程启动和对象传输开销覆盖了计算收益；
- MkDocs：为了保护共享对象加入锁后，关键步骤仍被串行执行，没有获得加速。

这些结果让我把问题从“怎样让 Agent 多生成一些并行代码”改成：

> **Agent 在真实项目中经常只看见可并行的循环，却没有看清循环外的数据和状态怎样
> 穿过 Worker 边界。并行方案是否正确、是否更快，很大程度上由这条边界决定。**

原始候选、测试错误和人工标签保存在：

- `docs/data/m8-manual-failure-labels.json`
- `docs/data/m8-failure-audit.json`
- `docs/data/m8-failure-audit.csv`

## 2. 公开大型项目中的参考证据

为了避免结论只来自自己选择的四个项目，我从 SWE-efficiency 的公开任务中复现了两个
scikit-learn 专家补丁。它们只作为“问题确实存在”的参考，不作为本项目 Agent 的成绩。

### scikit-learn #28064

原实现依次为 20 个特征计算分箱阈值。专家补丁把各特征作为独立任务，使用 4 个线程
并行执行。在固定输入和环境下：

- 原始中位时间：0.1075 秒；
- 专家补丁中位时间：0.0422 秒；
- 加速比：2.549x；
- 修改前后输出哈希一致；
- 54 项相关测试全部通过。

这个案例说明，真正需要判断的不只是“循环是否独立”，还包括底层计算是否释放 GIL、
线程是否适合，以及并行结果怎样按原特征顺序放回。

### scikit-learn #29330

原实现已经使用两个进程，但会把完整 DataFrame 交给每个转换任务，再在 Worker 内部取
所需列。专家补丁改为在提交任务前先切列，只把每个任务需要的数据传过去。在完全相同
的 Python、NumPy、pandas、joblib 和输入下：

- 原始中位时间：53.979 秒；
- 专家补丁中位时间：1.147 秒；
- 加速比：47.059x；
- 修改前后输出哈希一致；
- 354 项相关测试中 350 项通过、4 项因未安装可选依赖而跳过，失败为 0；
- 1000 行样本上的序列化代理量从“整表乘40个任务”降到“40个单列之和”，约减少
  39.23 倍。

这个案例尤其重要：它不是增加更多 Worker，而是重新选择 Worker 边界。并行框架没有
改变，任务算法也没有改变，仅减少边界上传递的数据就带来了数量级差异。

完整复现数据保存在 `docs/data/m8-reference-reproductions.json`。公开专家补丁与本项目
生成结果必须始终分开报告。

## 3. 研究问题

在相同模型、相同代码上下文、相同测试和相同运行次数下：

> **向代码 Agent 提供经过真实测量的 Worker 边界证据，能否比普通提示和只有热点信息
> 的方法生成更多“正确且真正加速”的项目级并行补丁？**

这里不把“安全回退”算成加速成功。系统拒绝错误补丁说明门控有效，但只有 Agent 自己
生成通过全部检查的补丁，才能计为有效并行化。

## 4. 核心观点（Insight）

本项目准备检验的观点是：

> **真实项目的并行化单位不应只由循环结构决定，而应由 Worker 边界决定。Agent 在修改
> 代码前，需要知道最小输入是什么、哪些状态不能跨进程、哪些对象会被线程共享，以及
> 传输成本是否会覆盖计算收益。**

这比“把性能分析结果发给 Agent”更具体。热点信息只能告诉模型“哪里慢”，Worker 边界
证据进一步回答“任务应该切在哪里、带什么数据、使用哪种执行方式”。

## 5. 方法：Worker 边界证据卡

对于已经定位的候选热点，系统先生成一张结构化证据卡，再让 Agent 设计修改。证据卡只
包含工具能够检查或实际测量的内容，不直接给出专家补丁。

```json
{
  "candidate_region": "候选函数或循环",
  "worker_unit": "一个Worker准备完成的最小工作",
  "worker_inputs": ["实际需要的输入"],
  "worker_outputs": ["需要返回的结果"],
  "state_risks": ["全局状态、动态函数、插件、实例状态"],
  "picklability": "输入能否被进程序列化",
  "full_payload_bytes": 0,
  "projected_payload_bytes": 0,
  "thread_probe": "样本运行结果",
  "process_probe": "样本运行结果",
  "ordering_and_merge": "怎样保持输出顺序和合并结果"
}
```

证据来自三类检查：

1. **代码检查**：读取变量、写入变量、实例状态、全局对象、闭包和结果合并方式；
2. **边界试验**：尝试序列化代表性输入，比较完整输入和最小输入的字节数；
3. **小样本执行**：在相同输入上比较串行、线程和进程，检查输出哈希和运行时间。

这张卡的作用不是替 Agent 写代码，而是把以往最容易被忽略的运行事实放进它的决策依据。

## 6. 对照实验

### B1：普通仓库级 Agent

- 看到任务说明、项目文件、测试反馈和性能结果；
- 不提供人工提示和 Worker 边界证据。

### B2：位置提示 Agent

- 在 B1 基础上只提供可能需要修改的函数和精确源码范围；
- 不提供 Worker 单元、后端选择、最小输入或传输成本；
- 用来区分“知道去哪里改”和“知道怎样切任务”是否是两回事。

### B3：Worker 边界证据 Agent

- 在 B2 基础上提供结构化边界证据卡；
- 模型、温度、读取次数、编辑轮数、测试和性能门槛与 B1/B2 相同。

### B4：公开专家补丁

- 只提供参考上界；
- 不参与 Agent 成功率计算；
- Agent 运行前不能看到补丁内容。

每个任务、每个 Agent 组至少独立运行 3 次。主结果使用公开大型项目任务；早期四个项目
只作为问题发现集，不与新结果混在一起。

### M8.1 冻结后的共同执行协议

正式实验前先用 `pilot-*` 编号检查实验管线，试运行结果全部排除，不进入主表。三组正式
实验共享下列设置：

- 使用同一个 DeepSeek 模型、温度、最大轮数、测试命令和性能门槛；
- 单次模型请求限时120秒，SDK最多重试1次；接口失败单独标记并补跑，不计为方法失败；
- Agent 只能做带源码哈希的局部修改，单次不能替换超过 120 行；
- 每次修改先做语法和结构检查，再运行项目原有测试、Ruff 与 Black；
- 快速反馈只和同一规模的快速基线比较，不能拿小样本候选和大样本基线相比；
- 正式计时使用“原始代码 → 候选代码 → 恢复原始代码”的前后夹测；
- 正式加速比用前后两次原始中位时间的中位数除以候选中位时间；
- 候选必须输出一致、项目检查通过且加速至少 1.05 倍，才算有效补丁；
- 回退、空补丁和只保留原始并行结构都不能算作新的优化成功。

2026年8月16日的 `pilot-11` 只用于验证上述管线：scikit-learn #28064 的候选通过54项
项目测试、Ruff、Black和输出检查，前后夹测加速为2.659倍。这个数字不进入正式结论，
也不会据此修改后续分组或指标。

协议执行后发现一次模型接口超过10分钟没有返回，而且尚未生成任何候选。该次运行记为
`28064/B1/formal-02` 基础设施失败并排除。为避免后续运行无限等待，M8.1只补充了上面的
统一API超时规则；模型、提示、测试、评价指标和已完成候选均未改变。B1将使用新的正式编号
补足第三个有效重复，原目录保留以便审计。

#29330首次管线试运行还发现，快速反馈使用1万行输入，而正式计时使用10万行输入，两者的
正确输出哈希本来就不同。旧适配器错误地要求它们匹配同一个哈希，因此在Agent运行前拒绝了
正常基线。修正后分别预登记快速和正式输出哈希；两种规模仍各自要求重复输出稳定，候选也只
和同规模基线比较。该次 `29330/B3/pilot-01` 保留为排除的管线检查，不进入正式结果。

## 7. 主要指标

- **有效补丁率**：测试通过、输出一致且加速至少 5%；
- **错误补丁率**：测试失败、输出变化或真实入口无法运行；
- **性能退化率**：正确但比原始项目慢 5% 以上；
- **边界问题率**：序列化、状态隔离、共享状态或传输问题占比；
- **中位加速比**：只在正确补丁上统计，同时报告失败和回退；
- **专家差距**：Agent 加速比与公开专家补丁加速比的差距；
- **修复轮数和 Token**：避免用无限尝试换取少量成功。

## 8. 可被否定的假设

- H1：B3 的有效补丁率高于 B1 和 B2；
- H2：B3 的边界相关错误率低于 B1 和 B2；
- H3：B3 在公开任务上的加速更接近专家补丁；
- H4：如果边界证据不能提高有效补丁率，只能降低错误交付，那么结论应写成“更安全”，
  不能写成“更会并行”。

如果 B3 没有改善，核心观点就没有得到支持。不能只展示其中一次成功，也不能把保留串行
代码算成并行化成功。

## 9. 当前限制与下一步

目前的 55.2% 来自 30 个候选修改的人工主因编码，样本仍小，而且一个候选可能同时存在
多个问题。两个 scikit-learn 案例复现的是公开专家补丁，不是 Agent 结果。因此下一步必须：

1. 固定证据卡格式和三个对照组，不再根据结果临时改变指标；
2. 把公开任务接入同一套 Agent 执行、测试和性能环境；
3. 先做一轮试运行检查实验管线，再完成每组至少 3 次正式实验；
4. 单独报告失败案例和不支持假设的结果；
5. 最后再写完整报告，避免先有结论再挑数据。

## 10. 与相关工作的区别

- PerfCodeGen 和 PerfAgent 说明执行反馈、热点剖析有用；本项目进一步研究并行化特有的
  Worker 边界证据；
- ParEval 和 ParEval-Repo 说明并行代码必须检查正确性与性能；本项目聚焦真实项目中任务
  输入、共享状态和后端选择造成的失败；
- SWE-Perf 和 SWE-efficiency 提供真实仓库性能任务和专家参考；本项目从其中筛选并复现
  与并行边界直接相关的任务，再进行受控 Agent 对照；
- 编译器自动并行化通常依赖静态依赖分析；本项目研究如何把静态检查与动态边界测量组织成
  Agent 能使用的证据，而不是重新实现一个完整编译器。
