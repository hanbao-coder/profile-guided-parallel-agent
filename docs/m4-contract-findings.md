# M4 语义契约实验记录

## 1. 这一步要验证什么

前一阶段的源码锚点让 Agent 更容易把修改落到真实代码中，但 6 次实验中没有
一个候选通过完整正确性检查。失败并不只来自语法错误，更常见的是 Agent 在跨进程
后改变了原程序的运行语义，例如：

- 父进程中临时替换的函数没有传到子进程；
- 单个文件失败时，程序的退出方式发生变化；
- 输出顺序或错误汇总方式发生变化。

因此，本阶段提出假设 H2：

> 在修改代码前，要求 Agent 基于实际源码写出一份可追溯的“并行化语义契约”，
> 会减少并行改写造成的语义错误。

这里的“契约”不是人工给出的标准答案，而是 Agent 在读过源码后必须明确写出的
约束，包括 Worker 的输入和输出、共享或运行时状态、输出顺序、错误和退出行为、
序列化风险、后端选择及回退条件。契约中的证据必须引用本轮实际读取过的源码片段
及其哈希，不能只凭模型记忆填写。

## 2. 实验设置

- 项目：Radon、Chardet。
- 每个项目独立运行 3 次，共 6 次。
- 每次从固定 commit 的干净副本开始。
- Agent 最多进行 12 轮交互、4 轮修改。
- 每个候选都运行项目完整测试、固定端到端工作负载和输出哈希检查。
- 串行基线、Agent 输入、每轮动作、补丁、测试输出和性能输出均保存。
- 对照关系：
  - B1：源码锚点，不要求语义契约；
  - B2：源码锚点 + 修改前语义契约。

## 3. 结果

| 方法 | 代码成功落地 | 完整语义正确 | 有效加速 |
|---|---:|---:|---:|
| B1：只有源码锚点 | 5/6 | 0/6 | 0/6 |
| B2：加入语义契约 | 6/6 | 4/6 | 0/6 |

B2 六次运行的详细结果如下。

| 项目 | 运行 | 测试与输出 | 相对串行加速比 | 结论 |
|---|---|---|---:|---|
| Chardet | 1 | 正确 | 0.969× | 正确，但没有有效提升 |
| Chardet | 2 | 正确 | 0.972× | 正确，但没有有效提升 |
| Chardet | 3 | 测试收集失败 | — | 正确性失败 |
| Radon | 1 | 正确 | 0.997× | 正确，但没有有效提升 |
| Radon | 2 | 正确 | 0.858× | 性能退化 |
| Radon | 3 | 输出哈希不一致 | 1708.681× | 快速失败，不是加速 |

所有加速比都以原始串行端到端中位数为分子。只有完整测试通过且输出哈希一致时，
性能数字才有解释意义。因此 Radon 第 3 次的 1708.681× 明确记为输出失败，不能
作为性能结果。

## 4. 观察到的现象

### 4.1 语义契约确实提高了正确候选比例

B1 中，Agent 虽然大多能改到代码，但 6 次候选全部有语义错误。加入契约后，
4 次候选通过完整测试和输出检查。这支持 H2，但样本仍小，只能作为当前项目上的
初步证据，不能声称对所有 Python 项目都成立。

### 4.2 “正确”不等于“更快”

Chardet 的两个正确候选为了避免 Windows 子进程丢失运行时替换函数，直接在
Windows 上退回串行执行。这样保住了语义，但自然没有加速。Radon 的正确候选则
选中了开销较大或覆盖范围不足的并行位置，一个基本持平，另一个慢约 14%。

这说明语义契约主要解决“改完是否仍是同一个程序”，不能单独解决：

- 并行位置是不是端到端热点；
- 任务是不是足够重；
- 进程启动和数据传递开销是否值得；
- 回退条件是否过于保守；
- 当前后端在真实机器上是否有效。

### 4.3 必须先检查正确性，再解释性能

Radon 第 3 次运行只用了约 0.008 秒，看起来比串行快上千倍，但输出哈希不同。
它实际上是候选没有完成原工作负载。这个案例说明，自动并行化研究中不能只记录
时间；完整测试、稳定输出和端到端结果一致性必须是性能比较的前置条件。

## 5. 当前得到的 insight

目前证据支持一个逐层关系：

1. 源码锚点解决“修改能否可靠落到真实项目”；
2. 语义契约解决“跨并发边界后是否仍保持原行为”；
3. 但只有把真实性能结果再次反馈给 Agent，才能解决“正确候选是否值得保留”。

因此下一阶段不再继续增加静态字段，而是验证 H3：

> 对已经通过正确性检查的候选，提供结构化的端到端性能反馈，并要求 Agent 在
> “修正方案或安全回退”之间作出选择，可以减少性能退化，并提高有效加速比例。
