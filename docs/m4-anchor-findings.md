# M4-B1 源码锚点对照结果

## 1. 唯一改动

B1 与 M3 的直接 Agent 使用相同项目、模型、轮数、探索次数、测试和性能工作负载。唯一变化是
编辑协议：

- B0：模型提交一段“旧文本 + 新文本”，执行器尝试在当前文件中寻找旧文本；
- B1：模型必须先读取准确行段，获得该段内容哈希，再用“文件 + 行范围 + 哈希 + 新文本”
  提交修改。

文件变化后旧哈希立即失效。锚点不提供并行方案，也不判断方案是否正确。

## 2. 协议校准

正式运行前排除了两次实现校准：

1. 第一个版本在工作记忆中保留了源码，但漏掉哈希；
2. 第二个版本允许模型把全部探索次数用于整文件读取，没有给精确行段读取留下预算。

修正后仍保持总探索预算为 6，只预留其中 1 次给 `read_lines`，没有为 B1 增加总轮数。
两次校准的原始回答和排除原因均保留。

## 3. 六次正式结果

| 项目 | 运行 | 是否落盘 | 正确性 | 潜在性能 |
|---|---|---:|---|---:|
| Radon | 1 | 是 | 测试收集失败 | 无效 |
| Radon | 2 | 否 | 保持串行基线 | 无候选 |
| Radon | 3 | 是 | 测试收集失败 | 无效 |
| Chardet | 1 | 是 | 3 项测试失败，固定输出一致 | 2.84 倍 |
| Chardet | 2 | 是 | 3 项测试失败，固定输出一致 | 2.68 倍 |
| Chardet | 3 | 是 | 3 项测试失败，固定输出一致 | 2.59 倍 |

B1 的补丁落盘率为 5/6；相同两个项目的 B0 落盘率为 3/6。B1 没有产生任何通过全部
正确性门槛的候选。

## 4. 对 H1 的判断

现有小样本对“源码锚点提高补丁落盘率”提供描述性支持，但不能给出统计显著性结论：

- 落盘率由 3/6 提高到 5/6；
- Radon 仍有 1 次使用模型编造的空文本哈希，被执行器拒绝；
- 锚点使更多并行方案进入真实测试，也暴露出更多语义问题。

因此锚点适合作为后续研究的基础设施，但它本身不是完整的自动并行化方法。

## 5. 稳定出现的语义失败

Chardet 三次独立运行都生成了相近的多进程方案，并稳定失败同 3 项测试：

1. 所有输入均失败时，没有保持原入口的退出行为；
2. 父进程中动态替换的 `chardet.detect` 没有传播到子进程；
3. 与动态替换相关的语言输出因此发生变化。

一般化后，进程边界不仅传递显式函数参数，还会改变：

- 运行时动态绑定、插件、依赖注入和 monkeypatch；
- 异常累计与最终退出条件；
- 输出顺序和输出位置；
- 可序列化状态与子进程重新导入的模块状态。

Radon 的两份落盘补丁则通过大范围重写破坏模块结构，说明还需要限制修改范围并在编辑前明确
Worker 输入、输出和状态边界。

## 6. 下一步

B2 不直接针对三个测试名称修补，而要求 Agent 在编辑前声明可追溯的并行化契约：

- Worker 输入和输出；
- 父进程状态与动态绑定；
- 顺序和聚合方式；
- 单项异常和整体退出行为；
- 进程可序列化风险；
- 选择线程、进程或串行回退的理由。

B2 与 B1 使用相同锚点。若 B2 不能降低正确性失败率，就否定“结构化语义契约足以改善
并行改写”的假设，并继续寻找其他原因。
