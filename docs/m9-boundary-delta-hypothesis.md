# M9 预注册：用关系约束完成跨 Worker 边界的数据投影迁移

## 1. M8 为什么没有支持原假设

M8 在两个 scikit-learn 真实性能任务上比较普通 Agent、位置提示和 Worker 边界证据，每组
独立运行3次。排除1次没有产生任何候选的API故障后，共有18次正式运行：

- 只有1次补丁同时通过项目检查、输出检查、语义检查和性能门槛；
- 6次最后因代码结构问题回退；
- 6次最后因项目正确性问题回退；
- 4次没有形成代码修改；
- 1次先通过原测试和性能门槛，但在补充语义审计中失败。

边界证据组在两个任务上的有效率都是0/3，因此“把更多边界信息写进提示，就能提高最终
并行补丁成功率”没有得到支持。完整数据见 `docs/data/m8-formal-summary.json`。

## 2. 从失败中发现的新问题

scikit-learn #29330 的优化不是只改一个循环。原代码在调用方把完整 DataFrame 和列选择器
一起交给并行 Worker，Worker 收到后再切列。要减少传输，至少要成套完成以下变化：

1. 调用方在提交任务前切出所需列；
2. 调用方不再传递列选择器；
3. `_transform_one` 和 `_fit_transform_one` 都删除对应参数；
4. 两个 Worker 都删除内部切列；
5. import 同步移动；
6. 原有 `Parallel(n_jobs=self.n_jobs)` 调度策略和结果顺序保持不变。

M8 的自由编辑经常只完成其中一部分，因而出现语法错误或调用参数不一致。另一个典型候选
把并行后端直接固定成线程，在登记工作负载上达到91.225倍表面加速，但覆盖了调用者选择的
`loky` 后端。它说明只优化一个基准数字会诱导 Agent 走“改变控制语义”的捷径。

## 3. 新的 Insight

> **跨 Worker 边界的数据优化不是一个局部代码修改，而是调用方与 Worker 之间的关系迁移。
> 正确方法必须把所有相关变化作为一个原子 Delta，同时把调度后端、Worker数量、结果顺序
> 等控制语义写成不可破坏的约束。**

因此，问题不只是 Agent 缺少事实，也不只是需要更多测试。自由文本计划与自由文本补丁之间
存在“落地断层”：模型可能说对方向，却无法保证多个文件中的参数、调用和状态同步变化。

## 4. 方法：Verified Boundary Delta

M9增加一个窄而明确的中间表示，不让模型直接自由改写整段源码。

### 4.1 从原代码发现关系

AST分析器只读取固定基础版本，自动检查：

- `delayed(func)` 调用当前传入的 `X` 和 `columns`；
- 两个 Worker 都接收 `columns`；
- 两个 Worker 内部都执行 `_safe_indexing(X, columns, axis=1)`；
- 调度器当前为 `Parallel(n_jobs=self.n_jobs)`，没有硬编码后端。

分析结果保存为 `docs/data/m9-boundary-delta-evidence.json`。生成脚本不读取公开专家补丁。

### 4.2 Agent声明关系 Delta

Agent仍需阅读真实源码并声明计划，但计划必须明确：

- 哪个调用函数移动数据投影；
- payload参数、selector参数和投影函数分别是什么；
- 哪些 Worker 必须同时更新；
- 是否删除Worker侧selector；
- 是否保持原调度策略。

计划缺少任何一个Worker或试图改变调度策略时，工具拒绝执行。

### 4.3 原子变换与关系检查

工具使用当前源码哈希和守卫片段执行成对变化。变换后立即用AST检查：

- 数据只在提交前投影一次；
- selector已从调用方和所有Worker删除；
- Worker内部不再重复投影；
- `n_jobs=self.n_jobs`保持不变；
- 没有新增 `backend`、`prefer` 或 `require` 等后端限制。

这不是通用自动重构器。当前只支持“把Worker内部数据投影移动到提交前”这一种模式，目的
是深入验证一个具体问题，而不是继续堆叠更多并行功能。

## 5. 对照与实验协议

- B1、B2、B3使用M8已冻结的3次正式结果；
- B4为Verified Boundary Delta，独立调用Agent 3次；
- E1为公开专家补丁，只作参考上界，不计入Agent成功率；
- B4使用同一DeepSeek模型、12轮、项目提交、输入、350项测试和1.05倍性能门槛；
- B4额外接受关系验证和调用者后端保持检查，这是新方法要解决的问题；
- 每个候选仍做“原始代码—候选—恢复原始代码”前后夹测；
- pilot运行只检查管线，不进入正式结果。

## 6. 预注册假设

- H5：B4的结构化计划有效率高于M8三个自由编辑组；
- H6：B4至少在2/3运行中生成通过项目测试和后端语义检查的补丁；
- H7：通过关系检查的B4补丁在正式工作负载上达到至少1.05倍加速；
- H8：如果B4只能靠固定模板复现唯一补丁，则结论必须限定为该边界迁移模式，不能宣称解决
  任意项目并行化。

## 7. 主要指标

- 计划是否通过关系模式验证；
- 是否一次原子变换成功；
- 项目测试、格式检查和后端语义检查结果；
- 正式配对加速比；
- 生成补丁与专家补丁的结构差异；
- Agent轮数、Token和基础设施失败；
- 对照组中结构错误、正确性错误和无修改的比例。

## 8. 当前结论边界

M9只研究已经存在并行调度、但Worker收到过大输入的项目级场景。它不能证明Agent可以自动
并行化任意串行项目，也不能证明所有数据投影都能安全前移。最终报告必须把“问题发现集、
M8被否定的假设、M9方法实验和公开专家上界”分开呈现。

## 9. 正式结果（2026-08-16）

pilot只用于检查实验流程，不计入正式结果。原计划独立运行3次；完成2次后，由于模型与
计算资源限制，取消第3次。这个变化发生在看到前两次结果之后，因此必须如实记录，不能把
2次结果写成预注册的3次，也不据此声称统计显著性。

| 方法 | 有效次数 | 项目测试 | 后端语义 | 正式配对加速比 |
|---|---:|---|---|---:|
| B1 普通Agent | 0/3 | 部分候选失败或回退 | 未全部满足 | 无有效结果 |
| B2 位置提示Agent | 0/3 | 曾出现表面通过候选 | 有1个候选改变后端语义 | 无有效结果 |
| B3 边界说明Agent | 0/3 | 候选未形成有效补丁 | 未形成有效候选 | 无有效结果 |
| B4 Verified Boundary Delta | 2/2 | 两次均350通过、4跳过 | 两次均保持loky | 48.77×、47.69× |

B4两次正式运行的加速比中位数为48.23×。两次都只进行1轮代码修改，并生成了相同的最终
补丁哈希。未经修改代码的配对基线分别为53.44秒和61.49秒；候选分别为1.10秒和1.29秒。
机器状态会造成基线波动，因此结论主要依据每次运行内部的前后夹测，而不是直接比较两次
实验的绝对时间。

这组结果支持当前场景下的核心观点：问题不只是“LLM知不知道该改哪一行”，而是自由编辑
很难保证调用方、Worker参数、Worker内部操作和调度策略同时一致。让Agent声明关系变化，
再由带守卫的原子变换执行，可以避免只改一半，也可以阻止通过硬编码线程后端获得虚假加速。

结论仍严格限定在“将Worker内的数据投影前移到任务提交处”这一类关系重构。当前证据不能
外推到任意仓库或任意并行化问题；后续需要在更多具有相同边界模式的真实项目中验证迁移性。
机器可读汇总见 `docs/data/m9-formal-summary.json` 和
`docs/data/m9-formal-summary.csv`。
