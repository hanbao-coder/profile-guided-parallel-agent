# M2 真实项目筛选记录

## 1. 这一阶段解决什么问题

旧实验只运行仓库里人为编写的单文件示例，无法回答 Agent 面对真实项目时会在哪一步出错。M2 的任务不是开始证明某个方法有效，而是先找到一批能够公平、重复运行的真实项目。

筛选时要求每个项目都满足：

- 是公开维护的多文件 Python 项目；
- 固定到具体提交，不随上游更新漂移；
- 原项目测试能够通过；
- 有真实的批处理或 CPU 计算入口；
- 输入固定，串行输出可以自动比较；
- 端到端时间至少达到数秒，能够观察并行化收益和开销；
- 许可证允许研究和保存修改补丁。

## 2. 第一批通过筛选的项目

| 项目 | 真实工作内容 | 为什么适合观察并行化问题 | 固定版本 |
|---|---|---|---|
| Radon | 批量读取 Python 文件并计算代码复杂度 | 文件之间看似独立，但结果要汇总为统一 JSON，适合观察 Agent 能否找到真实批处理边界 | `54b88e5` |
| Vulture | 扫描多个 Python 文件，查找没有使用的代码 | 同一个分析器会连续积累多个文件的信息，文件之间并非完全独立，适合观察共享状态和跨文件语义 | `2c21cb0` |
| Chardet | 批量读取不同编码的文件并判断字符编码 | 单个文件天然可分，但输出顺序、异常计数和文件读取仍属于原入口语义 | `ac49ec6` |

三者都不是为了本实验临时编写的循环示例。它们分别提供了“较容易拆分”“存在共享分析状态”“容易拆分但要保持入口行为”三种不同结构。这里只说明它们能产生不同现象，不预设哪一种问题最终最重要。

## 3. 原项目测试结果

| 项目 | 未修改版本的测试结果 | 说明 |
|---|---:|---|
| Radon | 399 通过，5 跳过 | 首次运行缺少开发依赖 `pytest-mock`，按项目开发依赖补齐后通过 |
| Vulture | 297 通过 | 首次运行缺少白名单测试使用的可选依赖 `pint`，补齐后通过 |
| Chardet | 9325 通过，21 个预期失败 | 排除 1 个需要 Windows 创建符号链接权限的环境测试；该测试不涉及编码检测算法 |

这里把“环境没有装全”和“项目功能错误”分开。缺少测试依赖只影响基线搭建，不能被统计成 Agent 并行化失败。

## 4. 固定工作负载和串行基线

全部工作负载均预热 1 次、正式运行 5 次，报告中位数。运行时将数值库线程数固定为 1，避免候选项目自己额外开线程。

| 项目 | 固定输入 | 串行中位时间 | 输出检查 |
|---|---|---:|---|
| Radon | 实验环境中按路径排序后的前 1800 个 Python 文件 | 13.402 秒 | 解析 JSON 后比较对象，不比较 JSON 文本顺序 |
| Vulture | OpenAI Python 包的完整源码目录 | 3.866 秒 | 比较规范化后的未使用代码记录 |
| Chardet | 官方 test-data 中按路径排序后的前 500 个文件 | 3.232 秒 | 逐文件比较编码检测记录，并保留输入顺序 |

五次正式运行中，三个项目的规范化输出哈希都保持一致。原始计时和完整输出保存在本机 `work/candidate-results/`，正式诊断运行会写入 `results/diagnostic/<project>/<run-id>/`。

## 5. 为什么需要专门的工作负载适配器

三个项目原本的命令行参数和输出格式不同，直接比较会把输入差异误当成方法差异。`scripts/run_candidate_baseline.py` 只做四件事：

1. 固定并排序输入；
2. 调用项目原本的分析函数或命令入口；
3. 统一执行 1 次预热和 5 次正式计时；
4. 将输出转成稳定 JSON，并计算哈希。

它不替换项目算法，也不提供并行实现。Agent 修改前后使用同一个适配器，因此测到的差异来自候选补丁，而不是测量脚本变化。

## 6. 筛选中遇到的问题

### 6.1 Git 下载不稳定

直接通过 Git 克隆时多次出现连接重置。为避免仓库版本漂移，改用 GitHub 的源码归档下载，并另外记录上游提交哈希。正式实验仍以清单中的提交为唯一版本标识。

### 6.2 Chardet 的源码归档没有 Git 元数据

Chardet 使用 Git 提交信息生成版本号。源码归档不含 `.git`，第一次安装因此失败。解决方法是在隔离环境里设置明确的开发版本号，再按项目原构建方式安装。这个问题属于打包环境问题，不属于并行化问题。

### 6.3 正确性不能只比较输出文件哈希

Radon 的两份 JSON 文本可能因为键顺序不同而产生不同文件哈希，但解析后的内容完全相同。因此正式判定使用“规范化后的数据结构相等”，不把无关的排版或键顺序当成错误。

### 6.4 Windows 符号链接权限

Chardet 有一项测试需要创建目录符号链接，普通 Windows 进程没有该权限。其余 9325 项测试通过。正式记录明确排除该环境测试，不会声称“全部测试无条件通过”。

## 7. 当前能下的结论与不能下的结论

目前可以确认：

- 已经从单文件示例转向了真实多文件项目；
- 三个项目能够从固定版本安装、测试和重复计时；
- 正确性判定覆盖项目测试与固定端到端输出；
- 不同项目包含不同的状态、聚合和入口约束。

目前仍不能确认：

- 通用 Agent 最常见的失败是什么；
- 共享状态是否比任务粒度更重要；
- Agent 是否会找到正确热点；
- 哪一种改进方法最有效。

这些问题必须由下一阶段每项目至少 3 次独立 Agent 运行来回答。

## 8. 诊断运行器校准

在正式统计前先用 Radon 和 Vulture 做了运行器校准。校准样本不进入最终频率表，但全部失败记录仍保留。主要修正包括：

- 增加按行号读取，避免大文件中间内容无法查看；
- 限制探索次数，避免模型一直读文件而不形成修改；
- 使用 Pro 处理方向判断、代码修改和修复，Flash 处理普通查找；
- 工作记忆只保留最近且相关的源码，避免每轮重复携带全部历史；
- 同一文件的多处修改先在内存中按顺序合并，再一次写入；
- 精确替换失败时，只在首尾锚点唯一、相似度不低于 0.80 时使用上下文匹配；
- 测试失败的候选只运行一次诊断工作负载，不把其速度写入有效性能结论。

校准过程中曾出现一个值得后续继续观察的现象：Radon 的一个候选表面达到约 9.87 倍加速，但 399 项测试中有 2 项失败，候选输出也与串行输出不同。直接原因是 Agent 把带动态配置的 `Harvester` 对象作为绑定方法送入 Windows 子进程，反序列化时发生递归错误。这一结果目前只作为定性案例，不能在其他项目重复出现前上升为最终 insight。
