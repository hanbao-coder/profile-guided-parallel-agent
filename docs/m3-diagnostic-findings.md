> `PYTHONPATH`，实际导入了已安装的原始包，因此全部排除。本文涉及 Chardet 的
> 频率和案例不再作为正式证据；修正原因见
> `docs/m5-protocol-correction-import-and-pairing.md`。Radon 与 Vulture 结果不受影响。

## 1. 诊断问题

本阶段不预先假定依赖分析、任务粒度或调度一定是核心问题，而是先回答：

> 通用代码 Agent 在真实多文件 Python 项目中尝试串行到并行转换时，主要失败发生在哪里？

统一 Agent 在 Radon、Vulture、Chardet 三个项目上各独立运行 3 次。每次最多探索 6 次、
总计 12 轮、允许初始修改加 3 次修复。项目测试、固定端到端工作负载和规范化输出比较均由
外部执行器完成，模型不能自行宣布成功。

## 3. 主要观察

### 3.1 第一层瓶颈是证据与修改脱节

多数运行能够找到大致入口，也会提出线程池或进程池方案，但生成的替换片段经常来自模型
记忆中的另一版代码结构，无法对应刚读过的文件。这个问题跨三个项目重复出现。

它属于通用仓库 Agent 的编辑/上下文问题，不能直接当成“并行化算法创新”。后续实验必须
先用更可靠的源码锚点控制这一变量，否则无法观察真正的并行化能力。

### 3.2 补丁落盘后，失败具有明显的并行化特征

三个成功落盘的正式候选没有一个最终成功：

- Radon 把类结构和跨进程状态处理破坏，形成错误输出；
- Chardet 线程版保持语义，但 CPU 型检测没有从线程获得并行收益，反而慢约 18.7%；
- Chardet 多进程版有约 2.99 倍潜在加速，但改变了原入口的异常和测试语义。

这说明真实项目并行化不是“找到循环后选择一个 Executor”。并行边界同时决定：

- 哪些输入和配置跨 Worker 传递；
- 状态如何合并；
- 结果顺序是否保持；
- 异常、退出行为和现有测试是否保持；
- 线程还是进程更适合；
- 调度、启动和传输成本能否被计算收益覆盖。

### 3.3 项目测试、工作负载输出和性能缺一不可

诊断中出现了三种容易误判的情况：

1. 退出码为 0、速度很快，但输出已经变成异常记录；
2. 固定工作负载输出正确，但项目其他接口测试失败；
3. 项目测试和输出都正确，但并行版更慢。

因此有效成功必须同时满足：项目测试通过、固定输出一致、端到端中位耗时至少改善 5%。

## 4. 人工参考版本（后续已更正）

为判断 Radon 是否本来就无法并行，另外实现了不计入 Agent 成功率的人工参考版本。它只把
文件名和必要布尔参数送入子进程，原项目的排序函数保留在主进程执行。

- 399 项测试通过，5 项跳过；
- 5 次输出哈希均与串行基线一致；
- 旧记录曾报告中位耗时由 13.402 秒降至 2.240 秒、约 5.98 倍加速；
- 该性能结论没有在后续固定协议复核中重现，不能继续作为人工上界。

后续 B0/B3 配对复核得到 12.7008 秒和 12.7182 秒，即 0.9986 倍；输出仍保持一致。能够保留的
结论只有参考修改在语义上正确，不能据此证明 Radon 固定负载存在明显并行收益。详见
`docs/reference-upper-bound.md`。

## 5. 实验中排除的记录

所有排除记录和原因仍保留在 `results/diagnostic`。主要包括：

- Agent 工具能力尚未冻结的协议校准；
- DeepSeek 外部服务延迟；
- Windows 公共临时目录权限问题；
- Chardet 早期工作负载绕过被修改 CLI 的适配器错误。

Chardet 的适配器错误被发现后，旧三轮全部排除，改为直接调用公开 CLI、重建串行基线并
重新运行 3 次。环境或实验器错误没有混入 Agent 失败频率。

## 6. 目前不能下的结论

- 不能因为 6/9 补丁未落盘，就声称依赖关系是最大问题；
- 不能因为 Chardet 线程版变慢，就声称线程永远不适合；
- 不能因为人工 Radon 方案成功，就声称“最小状态传递”已经跨项目成立；
- 不能用 3 个项目推断所有 Python 仓库；
- 不能把通用编辑接口改进本身包装成并行化方法。

## 7. 下一阶段研究方向

下一阶段先把“补丁能否准确落到真实代码”作为受控变量，再研究并行化特有约束。候选假设是：

> 相比直接从仓库生成并行补丁，先建立可追溯到源码的并行化契约，再选择并行边界和执行
> 机制，可以提高补丁可执行率，并减少正确性失败和性能退化。

该假设仍需用 Anchor-only、Contract-only 和完整方法的对照实验验证，不能仅凭当前观察
直接宣布成立。
