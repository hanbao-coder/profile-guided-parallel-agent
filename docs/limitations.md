# 当前局限与下一步

## 1. 样本规模有限

主实验只有 4 个真实项目，每种方法 12 次独立运行；MkDocs 消融每组只有 3 次。当前结果适合
展示反复出现的失败和验证机制作用，不足以估计所有 Python 项目的平均成功率。

## 2. 自动加速成功率仍低

完整方法只有 1/12 次得到有效并行版本。其主要贡献目前是避免错误交付，而不是已经解决了
项目级自动并行化。安全回退必须单独报告，不能与加速成功合并。

## 3. 方法包含多个共同变化

完整方法同时加入源码来源检查、锚点、语义契约、性能反馈和回退。MkDocs 消融只单独观察了
“去掉反馈与回退”后的表现，还不能精确分离每个部件在四个项目上的贡献。

## 4. 只覆盖单机 CPU 并行

本阶段使用 Windows 单机进程或线程执行，研究的是项目修改、语义保持和端到端收益，不涉及
真实多节点网络通信、GPU 或异构资源调度。以后接入 Ray 多节点时需要重新测量序列化、网络和
节点故障成本。

## 5. 依赖现有项目测试

项目测试和固定输出能发现很多错误，但不能证明所有输入上的行为完全一致。特别是插件、副作用、
日志顺序和异常时机，可能仍有未覆盖情况。

## 6. 下一步优先方向

下一阶段不继续堆叠新的调度功能，而优先研究：

1. 从测试失败中自动提取“哪些状态不能跨 Worker”的证据；
2. 让 Agent 优先生成状态最小的顶层 Worker，而不是直接把复杂对象送入进程池；
3. 在更多具有批处理入口的真实项目上重复实验；
4. 对源码锚点、语义契约和反馈回退分别做更完整的消融；
5. 报告 Agent 调用、Token 和实验时间，分析自动优化的实际成本。
