# M7 Worker 边界证据实验：终止说明

## 1. 原假设

Radon 的一次失败补丁把绑定实例方法直接交给进程池，导致整个对象和动态配置跨进程传递。
M7 原本提出假设：如果自动发现这类高把握风险，并把具体源码位置反馈给 Agent，Agent 可能更
容易生成模块顶层、只传少量数据的 Worker，从而提高正确候选或有效并行候选的比例。

这个实验只增加 Worker 边界检查，其余模型、提示、测试、固定输出和性能门槛保持不变。

## 2. 为什么没有继续补第三次 Agent 运行

M7 开始时使用了一条旧前提：人工写出的状态最小版本约有 5.98 倍加速，因此 Radon 被当作
“边界写对后一定有明显收益”的案例。正式补跑前，项目先用当前固定协议重新验证了这个前提。

复核结果为：

| 版本 | 中位耗时 | 相对 B0 加速 | 输出一致 |
|---|---:|---:|---:|
| B0 原始串行 | 12.7008 秒 | 1.0000 倍 | 是 |
| B3 人工参考 | 12.7182 秒 | 0.9986 倍 | 是 |

B3 没有达到预先规定的 1.05 倍门槛。因此即使 Agent 完全学会这条边界写法，也没有证据表明它
能在该工作负载上获得有效加速。继续消耗模型调用补齐第三次运行，无法回答原先的性能假设。

## 3. 已完成的探索性运行

边界检查实现完成后有 2 次有效 Agent 运行，均未产生有效并行版本：一次检查到真实的实例状态
跨进程风险，但修复后输出仍不一致；另一次没有触发该规则，候选因测试失败或没有实际并行而
回退。

另有两次被排除：一次因汇总器把 Python 语法错误误分成边界错误；修正后的替代运行在首次
模型调用时遇到外部服务余额不足，未产生候选。这些记录保留，但不进入有效运行统计。

## 4. 结论边界

M7 不是“证明规则无效”，也不是“因接口余额不足而暂停”。更准确的结论是：

> 作为正确性诊断，Worker 边界检查能指出一类真实风险；但当前 Radon 人工参考版本没有可复现
> 的端到端收益，所以本案例不足以检验这条规则能否提高自动加速成功率。

因此 M7 按科研前提失效终止，不扩展到 Chardet，也不把两次探索运行包装成正式正负结论。
后续若继续研究，应先寻找一个经固定协议确认“人工并行版本确有收益”的真实项目，再预注册
对应的 Agent 生成假设。
