## 2026-08-07：研究方向重置与 M0 检查

### 当前研究问题

在多文件串行项目中，通用代码 Agent 能否在保持项目可运行和结果正确的同时，
获得端到端性能提升？如果不能，最常见且影响最大的失败发生在哪里？

最终研究问题尚未确定。依赖遗漏、热点定位、任务粒度和性能退化目前都只是候选
原因。

### 当日操作

1. 阅读并核对长期目标；
2. 检查仓库、README、`docs`、`tests`、`benchmarks`、历史结果和 Git 状态；
3. 阅读 `docs/related-work-project-level-parallelization.md`；
4. 使用当前 Python 环境运行旧版总验收和完整自动测试；
5. 建立项目级诊断实验协议和机器可读配置。

### 已验证事实

1. 当前 Git 远端为
   `git@github.com:hanbao-coder/profile-guided-parallel-agent.git`。
2. 工作区中有 7 个用户已删除的旧文档；这些删除保持不变。
3. 当前 `benchmarks` 中的 11 个工作负载均为单文件形式，不能证明项目级并行化
   能力。
4. 旧版完整测试使用独立临时目录后，76 项通过、2 项失败。
5. 两项失败均由旧验收器强制要求已删除的早期汇报文档导致，而不是算法测试失败。
6. 旧版总验收同样首先被这四个已删除的汇报文件阻断。
7. 仓库已经具备 Ray 执行、正确性比较、性能重复测量、DeepSeek 调用、日志保存和
   部分性能优化代码，可作为后续诊断实验的基础设施。

### 暂定解释

现有系统解决的是规范化单文件工作负载的执行与优化问题。它能帮助我们运行后续
实验，但目前没有证据说明通用 Agent 在多文件项目中最主要的失败原因是什么。

旧验收器把汇报材料和算法证据绑定在一起，说明旧阶段更偏向“交付一个演示包”。
新阶段需要把验收重点改为原始实验数据、代码补丁、运行日志和可复现结果。

### 尚未确认

- Agent 是否会获得局部加速但没有端到端收益；

## 2026-08-07：M2 第一批真实项目筛选

### 当日操作

1. 固定并下载 Radon、Vulture、Chardet 三个开源项目的具体版本；
2. 为每个项目建立隔离 Python 环境，按项目自身方式安装并运行测试；
3. 为三种不同入口建立统一的端到端工作负载适配器；
4. 每个项目预热 1 次、正式运行 5 次，检查运行时间和规范化输出；
5. 将环境问题、测试问题和工作负载问题分别记录，没有把环境缺依赖误记成 Agent 失败。

### 已验证事实

1. Radon 固定到提交 `54b88e5878b2724bf4d77f97349588b811abdff2`，399 项测试通过、5 项跳过；
2. Vulture 固定到提交 `2c21cb0ae2afa657e36f6a397cb573608a65d79e`，297 项测试通过；
3. Chardet 固定到提交 `ac49ec6e91c3e247b83ef78bbef0c78574b018a0`，排除 Windows 符号链接权限测试后，9325 项测试通过、21 项为项目标记的预期失败；
4. 三个项目都至少有 20 个 Python 源文件，并有真实命令行或批处理入口；
5. Radon、Vulture、Chardet 固定工作负载的串行中位时间分别为 13.402 秒、3.866 秒和 3.232 秒；
6. 三个项目五次运行的规范化输出都保持一致；
7. Radon 的原始 JSON 文本哈希可能因键顺序而变化，但解析后的 JSON 对象一致，因此正式正确性判定不能使用字节级文本比较。

### 遇到的问题与处理

- Git HTTPS 克隆多次连接重置，改用 GitHub 源码归档，并单独保存提交哈希；
- Vulture 测试需要可选依赖 `pint`，补齐后通过；
- Chardet 源码归档没有 Git 元数据，无法自动生成版本号；在隔离环境中设置固定开发版本号后完成安装；
- Chardet 官方测试语料需要额外下载，使用官方 test-data 的固定主分支归档；
- Chardet 有一项 Windows 符号链接测试因普通进程权限失败；该项与编码检测算法无关，单独排除并保留说明。

### 当前解释

这三个项目给出了不同的潜在困难：Radon 的文件任务较独立，Vulture 在一个分析器中积累跨文件状态，Chardet 的单文件检测较独立但原入口还包含顺序和异常处理。它们适合用来观察 Agent 在不同结构下的行为，但当前没有证据表明其中某一类就是最终研究问题。

### 尚未确认

- 通用 Agent 是否会先理解入口和共享状态，再选择并行边界；
- 它是否能在保持项目测试和黄金输出的同时获得端到端加速；
- 三个项目是否足以覆盖主要失败类型，还是需要补充更复杂的流水线或图项目；
- 最终 insight 和方法是什么。

## 2026-08-07：M3 项目级 Agent 运行器校准

### 当日操作

1. 实现受控项目级 Agent：可以查看目录、读文件、按行读取、搜索、修改代码，并且只能运行预先登记的测试与工作负载；
2. 接入 DeepSeek Pro/Flash 路由，Pro 用于方向判断和修改，Flash 用于普通查找；
3. 在 Radon 上进行多轮校准，保留所有无效运行并写明排除原因；
4. 在 Vulture 上检查严格整块替换是否会掩盖真正的并行化问题；
5. 将正式基线协议升级为 v2：6 次探索、12 个总回合、初始修改加 3 次修复、精确匹配优先、唯一上下文匹配作为后备。

### 已验证事实

1. DeepSeek 接口可用，服务端可见 `deepseek-v4-pro` 与 `deepseek-v4-flash`；
2. 不限制上下文时，Radon 一次 20 回合试跑消耗 475868 Token，且没有生成补丁；
3. Pro/Flash 路由和工作记忆裁剪后，相同规模运行降到约 13.1～13.5 万 Token；
4. 精确整块替换会让模型已找到修改位置后仍无法落盘，因此它属于通用编辑工具瓶颈，不应成为本研究的主要现象；
5. Radon 的一个初步候选成功加入进程池，端到端中位时间从 13.402 秒降至 1.357 秒，表面加速 9.874 倍；
6. 该候选有 2 项测试失败，输出哈希也与串行基线不同，因此不构成有效加速；
7. 失败堆栈显示，绑定的 `Harvester` 方法把包含动态 `Config` 的对象送入 Windows 子进程，反序列化时触发递归错误；
8. 项目把子进程异常包装成普通 `{error: ...}` 结果，导致程序仍能结束且速度很快，证明只看退出码和耗时会产生错误结论。

### 当前解释

初步证据说明，项目并行化不能只判断循环迭代是否独立，还要判断并行边界跨进程传递了什么对象、这些对象能否序列化、以及异常是否被项目正常输出掩盖。这个解释具有并行化特异性，但目前只在 Radon 的一个初步样本中确认，不能提前作为最终 insight。

### 协议变化与排除

- `pilot-*`：运行器能力不完整或上下文配置不合理，不进入统计；
- `preliminary-strict-run-*`：使用 exact-only 编辑协议，不进入 v2 频率表；
- 所有排除目录均保留模型原始回答、事件和排除原因；
- 从 protocol v2 起，只有 `run-01`、`run-02`、`run-03` 命名的运行进入正式统计。

### 下一步

1. 用 protocol v2 重新完成 Radon 的 3 次独立运行；
2. 完成 Vulture、Chardet 各 3 次运行；
3. 比较“并行边界状态传递”“共享跨文件语义”“输出顺序/异常语义”等问题是否重复；
4. 在跨项目数据出来前，不确定最终研究假设。

## 2026-08-08：M6 四项目主实验与 MkDocs 消融完成

### 当日操作

1. 完成 Radon、Vulture、Chardet、MkDocs 的修正后普通 Agent 实验，共 12 次；
2. 完成带源码来源预检、源码锚点、并行化契约、稳健性能反馈和安全回退的完整方法实验，共 12 次；
3. 在 MkDocs 上额外运行 3 次“只有源码锚点和语义契约、没有性能反馈与回退”的消融；
4. 将全部运行统一分类，并生成紧凑 JSON、CSV 和中文图表；
5. 更新研究问题、方法、实验、局限和复现文档；
6. 使用独立临时目录运行本项目 113 项自动测试，全部通过。

### 已验证事实

1. 普通 Agent 的 12 次运行中，6 次留下错误修改，6 次没有形成可用方案，0 次有效并行；
2. 完整方法的 12 次运行中，1 次有效并行、10 次安全回退、1 次未形成方案，没有留下已知错误修改；
3. 唯一有效结果来自 Chardet，配对端到端中位加速为 3.251 倍；
4. 完整方法实际检查 30 个候选：17 个测试失败、4 个输出或集成失败、3 个没有真实并行结构、3 个加速不足 5%、2 个整体变慢、1 个被接受；
5. MkDocs 消融中，普通 Agent 和只加语义契约均为 2 次错误修改、1 次没有方案；完整方法 3 次均回退到串行版本；
6. Radon 的人工状态最小版本可达到约 5.98 倍，说明完整方法在 Radon 上的回退不是因为工作负载本身绝对不可并行，而是 Agent 没有稳定找到正确边界；
7. Chardet 的早期 `src` 导入路径错误和 MkDocs 的工作目录错误均已写排除原因并替代重跑，不进入正式结论。

### 当前 insight

项目级自动并行化不是一次性生成并行语法，而是一个必须允许拒绝候选的决策过程。结构化语义说明可以帮助模型思考，但不能代替原项目测试、固定输出和配对端到端性能。证据不合格时保留串行版本，比强行交付并行补丁更可靠。

这个 insight 当前主要解决“错误交付”，不代表自动加速已经成功。有效并行率只有 1/12，下一阶段应研究如何从失败测试中提取状态边界，并提高安全候选的生成概率。

### 消融结论边界

MkDocs 消融每组只有 3 次，只能说明在该项目上反馈与回退阻止了错误交付，不能据此断言语义契约对所有项目都无效。完整方法同时包含多个变化，仍需扩大项目和运行次数，或继续拆分组件。
