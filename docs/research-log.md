本日志只记录可追溯的事实、暂定假设和下一步实验。旧版单文件 Ray 系统保留为

## 2026-08-07：研究方向重置与 M0 检查

### 当前研究问题

在多文件串行项目中，通用代码 Agent 能否在保持项目可运行和结果正确的同时，
获得端到端性能提升？如果不能，最常见且影响最大的失败发生在哪里？

最终研究问题尚未确定。依赖遗漏、热点定位、任务粒度和性能退化目前都只是候选
原因。

### 当日操作

1. 阅读并核对长期目标；
2. 检查仓库、README、`docs`、`tests`、`benchmarks`、历史结果和 Git 状态；
3. 阅读 `docs/related-work-project-level-parallelization.md`；
4. 使用当前 Python 环境运行旧版总验收和完整自动测试；
5. 建立项目级诊断实验协议和机器可读配置。

### 已验证事实

1. 当前 Git 远端为
   `git@github.com:hanbao-coder/profile-guided-parallel-agent.git`。
2. 工作区中有 7 个用户已删除的旧文档；这些删除保持不变。
3. 当前 `benchmarks` 中的 11 个工作负载均为单文件形式，不能证明项目级并行化
   能力。
4. 旧版完整测试使用独立临时目录后，76 项通过、2 项失败。
5. 两项失败均由旧验收器强制要求已删除的早期汇报文档导致，而不是算法测试失败。
6. 旧版总验收同样首先被这四个已删除的汇报文件阻断。
7. 仓库已经具备 Ray 执行、正确性比较、性能重复测量、DeepSeek 调用、日志保存和
   部分性能优化代码，可作为后续诊断实验的基础设施。

### 原始证据位置

### 暂定解释

现有系统解决的是规范化单文件工作负载的执行与优化问题。它能帮助我们运行后续
实验，但目前没有证据说明通用 Agent 在多文件项目中最主要的失败原因是什么。

旧验收器把汇报材料和算法证据绑定在一起，说明旧阶段更偏向“交付一个演示包”。
新阶段需要把验收重点改为原始实验数据、代码补丁、运行日志和可复现结果。

### 尚未确认

- 通用 Agent 在多文件项目中最常修改错误的位置是什么；
- 跨文件依赖问题是否比性能退化更常见；
- Agent 是否会获得局部加速但没有端到端收益；
- 哪种改进方法最值得在本项目中实现。

5. 在诊断结果出现之前不确定最终 insight。

## 2026-08-07：M1 新近相关工作核查

### 当日操作

核查2025—2026年的仓库级性能优化研究，新增 SWE-Perf、SWE-efficiency、
FormulaCode、PEACE 和 PerfAgent，并检查其论文页面、公开基准说明和主要评价
方法。

### 已验证事实

1. PerfAgent 于2026年7月发布，已经使用“热点剖析摘要、选择性测试、反复优化”
   改善通用代码 Agent 的仓库级性能优化结果。
2. SWE-efficiency 提供498个真实性能任务，覆盖9个主流Python仓库，并同时提供
   性能工作负载、仓库正确性测试和专家补丁。
3. FormulaCode、SWE-Perf和PEACE均已把一般代码性能优化扩展到真实仓库或多函数
   场景。
4. 因此，“给Agent加入性能剖析”不能单独作为本项目的创新点。

### 对现象的解释

本项目需要与一般仓库性能优化区分。当前仍值得诊断的是串行到并行转换特有的约束：
并发状态安全、任务划分、数据传递、运行时管理成本，以及局部并行是否带来端到端
收益。

### 尚未确认

上述并行化特有问题中哪一种最常阻断普通 Agent，仍必须由 M3 诊断实验决定。

## 2026-08-07：M2 第一批真实项目筛选

### 当日操作

1. 固定并下载 Radon、Vulture、Chardet 三个开源项目的具体版本；
2. 为每个项目建立隔离 Python 环境，按项目自身方式安装并运行测试；
3. 为三种不同入口建立统一的端到端工作负载适配器；
4. 每个项目预热 1 次、正式运行 5 次，检查运行时间和规范化输出；
5. 将环境问题、测试问题和工作负载问题分别记录，没有把环境缺依赖误记成 Agent 失败。

### 已验证事实

1. Radon 固定到提交 `54b88e5878b2724bf4d77f97349588b811abdff2`，399 项测试通过、5 项跳过；
2. Vulture 固定到提交 `2c21cb0ae2afa657e36f6a397cb573608a65d79e`，297 项测试通过；
3. Chardet 固定到提交 `ac49ec6e91c3e247b83ef78bbef0c78574b018a0`，排除 Windows 符号链接权限测试后，9325 项测试通过、21 项为项目标记的预期失败；
4. 三个项目都至少有 20 个 Python 源文件，并有真实命令行或批处理入口；
5. Radon、Vulture、Chardet 固定工作负载的串行中位时间分别为 13.402 秒、3.866 秒和 3.232 秒；
6. 三个项目五次运行的规范化输出都保持一致；
7. Radon 的原始 JSON 文本哈希可能因键顺序而变化，但解析后的 JSON 对象一致，因此正式正确性判定不能使用字节级文本比较。

### 遇到的问题与处理

- Git HTTPS 克隆多次连接重置，改用 GitHub 源码归档，并单独保存提交哈希；
- Vulture 测试需要可选依赖 `pint`，补齐后通过；
- Chardet 源码归档没有 Git 元数据，无法自动生成版本号；在隔离环境中设置固定开发版本号后完成安装；
- Chardet 官方测试语料需要额外下载，使用官方 test-data 的固定主分支归档；
- Chardet 有一项 Windows 符号链接测试因普通进程权限失败；该项与编码检测算法无关，单独排除并保留说明。

### 当前解释

这三个项目给出了不同的潜在困难：Radon 的文件任务较独立，Vulture 在一个分析器中积累跨文件状态，Chardet 的单文件检测较独立但原入口还包含顺序和异常处理。它们适合用来观察 Agent 在不同结构下的行为，但当前没有证据表明其中某一类就是最终研究问题。

### 尚未确认

- 通用 Agent 是否会先理解入口和共享状态，再选择并行边界；
- 它是否能在保持项目测试和黄金输出的同时获得端到端加速；
- 三个项目是否足以覆盖主要失败类型，还是需要补充更复杂的流水线或图项目；
- 最终 insight 和方法是什么。
