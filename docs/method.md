# 方法：带证据检查和安全回退的项目并行化 Agent

## 1. 设计目标

普通代码 Agent 往往在读到一个循环后就开始写线程池或进程池代码。本项目要求它在修改前后
回答三个问题：

1. 修改的是不是真实工作负载经过的代码？
2. 并行执行是否保持原项目的状态、顺序、异常和公开入口行为？
3. 整个项目从入口到输出是否真的变快？

只要其中一项没有通过，候选就不能作为最终版本保留。

## 2. 方法流程

```text
固定版本的串行项目
        ↓
运行原项目测试、固定工作负载和端到端计时
        ↓
Agent 阅读入口、调用链和相关状态
        ↓
生成“并行化契约”：任务输入输出、共享状态、顺序、异常、执行方式
        ↓
用源码位置和内容哈希约束修改位置
        ↓
生成候选并行代码
        ↓
源代码导入检查 → 项目测试 → 固定输出检查 → 配对性能测量
        ↓
通过：保留候选     未通过：把证据反馈给 Agent 修复
        ↓
超过轮数仍未通过：恢复原串行代码
```

## 3. 四个关键设计

### 3.1 源码来源和位置检查

真实项目可能同时存在源码副本和已经安装的旧版本。实验先记录实际导入文件的路径，避免测试
误用别处的包。Agent 修改代码时必须提供文件、行范围和原文哈希；源码变化后，旧修改不能
继续直接套用。

### 3.2 并行化契约

Agent 在写代码前先说明：每个任务拿到什么数据、返回什么结果、哪些状态只读、哪些结果需要
合并、输出顺序是否固定、异常如何传回，以及为什么选择线程或进程。契约的作用是让后续测试
能够针对明确风险检查，而不是把一段自然语言说明当作正确性证明。

### 3.3 配对性能反馈

候选版本与串行版本在同一次实验中使用相同机器、相同输入和相同测量方法。反馈阶段预热 1 次，
正式运行 3 次取中位数；最终测量预热 1 次、运行 5 次取中位数。这样可以减少后台负载或首次
启动造成的偶然快慢。

候选只有在项目测试通过、固定输出一致、确实存在并行结构，且端到端加速至少为 1.05 倍时才
被接受。5% 是预先固定的最低收益线，不是在看到结果后临时选择。

### 3.4 安全回退

如果候选测试失败、输出变化、没有实际并行、加速不足或变慢，系统把具体证据反馈给 Agent。
若限定轮数内仍无法修好，就撤销候选，恢复本次实验开始前的串行代码。回退不提高加速成功率，
但能避免把已经知道有问题的修改当作结果交付。

## 4. 与普通 Agent 的区别

| 项目 | 普通 Agent | 完整方法 |
|---|---|---|
| 修改位置 | 模型自行寻找 | 导入来源预检 + 源码锚点 |
| 并行语义 | 主要依赖模型理解 | 先形成任务和状态契约 |
| 正确性 | 最后运行一次检查 | 项目测试和固定输出逐轮门控 |
| 性能 | 最终测一次 | 候选阶段稳健反馈 + 最终配对测量 |
| 失败处理 | 可能留下错误补丁 | 达不到条件就恢复串行版本 |

## 5. 当前方法边界

方法并不保证每个项目都能被并行化。它目前更擅长判断“这个候选不能交付”，而不是稳定生成
高质量并行补丁。后续研究重点是从已记录的失败中改进任务边界和状态最小化，而不是继续增加
互不相关的功能。

## 6. 复现协议补充

四个候选项目、外部测试数据和输入环境分别固定版本。输出比较使用协议 v2：文件名先转换为
输入根目录下的相对路径，再计算哈希，避免本机目录变化被误判为语义变化。项目测试、固定
输出和性能验证顺序执行；从零搭建与核对入口见 `docs/reproducibility.md`。
