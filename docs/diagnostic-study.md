# 项目级自动并行化诊断实验规范

> 状态说明：本文记录形成研究问题之前的诊断协议。该阶段现已完成，正式结果见
> `docs/m6-findings.md`。后续 M7 曾针对诊断中出现的 Worker 边界问题做预注册检验；固定协议
> 复核发现人工性能参考不成立，因此该支线已经终止，详见 `docs/m7-worker-boundary-design.md`。

## 1. 实验目的

本阶段不比较某个优化模块是否有效，而是先回答一个更基础的问题：

> 当通用代码 Agent 直接尝试并行化一个可运行的多文件串行项目时，它会在哪些
> 阶段失败？

研究对象是完整修改过程，包括理解项目、选择修改位置、修改代码、接入原入口、
验证正确性和测量端到端性能。

## 2. 研究单位

一次独立实验由“一个固定版本的串行项目 + 一次全新的 Agent 运行”组成。同一个
项目至少进行 3 次独立 Agent 运行，不能只保留最成功的一次。

每个项目必须满足：

- 至少 3 个源代码文件；
- 有固定运行入口；
- 有确定性输入或固定随机种子；
- 有自动测试或黄金输出；
- 能够重复测量端到端时间；
- 包含 CPU 密集或批处理阶段；
- 许可证允许研究和保存修改补丁；
- 不是为了本实验临时拼出的单循环示例。

## 3. 项目选择

计划从以下类型中选择 4～6 个项目：

| 类型 | 选择原因 | 需要观察的问题 |
|---|---|---|
| 批量图像处理 | 文件读取、预处理和计算分散在不同模块 | 数据复制、任务粒度、流水线集成 |
| 文本或文件分析 | 多文件天然可拆分，但存在聚合和输出顺序 | 结果语义、归约、I/O占比 |
| 蒙特卡洛或参数搜索 | 通常存在明显并行机会 | 随机性、负载划分、端到端收益 |
| 多阶段数据流水线 | 一个阶段加速不一定改善总时间 | 热点定位、阶段边界、局部与整体 |
| 图或不规则计算 | 单项成本可能差异很大 | 负载不均衡、共享状态、依赖 |

选择项目时先验证可复现性，再决定是否纳入。项目规模不以代码行数越多越好，而以
“结构完整、可运行、问题可观察”为准。

## 4. 普通 Agent 基线

诊断阶段使用一个不带本项目改进方法的普通代码 Agent。所有项目固定：

- 同一模型和模型参数；
- 同一基础提示词；
- 同一工具权限；
- 相同最大修复轮数；
- 尽量接近的 Token 上限；
- 同一台机器和软件环境；
- 同一性能测量方法。

普通 Agent 可以阅读文件、运行命令、修改代码和根据错误进行最多 3 轮修复，但
不会获得我们后续可能提出的专用证据包或人工指定修改边界。

## 5. 单次运行流程

1. 复制固定版本的串行项目到独立工作目录；
2. 记录代码版本、依赖、系统、CPU、Python和并行框架版本；
3. 运行原项目测试和黄金输出；
4. 预热 1 次，正式运行 5 次，记录串行端到端中位数；
5. 启动一次全新 Agent，让它分析并完成并行化；
6. 保存 Agent 阅读过的文件、提示、回复、计划和代码补丁；
7. 安装或启动修改后的项目；
8. 运行原测试和额外黄金输出检查；
9. 正确后再进行 1 次预热和 5 次正式性能测量；
10. 保存修复过程、最终状态和失败分类。

每次正式性能实验设置：

```text
OMP_NUM_THREADS=1
MKL_NUM_THREADS=1
OPENBLAS_NUM_THREADS=1
PYTHONHASHSEED=0
```

项目自身需要随机数时使用固定种子。运行原版和候选版的顺序应交错或随机化，降低
机器温度和后台负载造成的顺序偏差。

## 6. 必须保存的证据

每次运行创建独立目录：

```text
results/diagnostic/<project>/<run-id>/
├── environment.json
├── baseline/
│   ├── test.log
│   ├── output.json
│   └── timings.json
├── agent/
│   ├── prompt.md
│   ├── response.jsonl
│   ├── files_read.json
│   ├── plan.md
│   ├── patch.diff
│   └── token_usage.json
├── candidate/
│   ├── test.log
│   ├── output.json
│   └── timings.json
└── outcome.json
```

`outcome.json` 至少记录：

- 是否成功安装或启动；
- 测试和黄金输出是否通过；
- Agent 修改了哪些文件和位置；
- 修改位置是否覆盖真实热点；
- 串行与候选端到端中位时间；
- 加速比和性能波动；
- 修复轮数；
- 最早阻断阶段；
- 主要失败类别；
- 可以同时记录的次要失败类别。

## 7. 初始失败分类和判断规则

| 类别 | 判断规则 |
|---|---|
| 环境/构建失败 | 修改后无法安装、导入、构建或启动 |
| 入口理解错误 | Agent绕过或破坏项目规定的运行入口 |
| 热点定位错误 | 修改区域不在主要耗时调用链，或只覆盖极少运行时间 |
| 跨文件依赖失败 | 漏掉调用方、配置、数据类型或跨文件状态 |
| 共享状态/副作用失败 | 并行后出现竞争、重复写入、顺序变化或状态不一致 |
| 正确性失败 | 原测试或黄金输出不通过 |
| 集成失败 | 并行实现单独可运行，但无法通过原项目入口工作 |
| 粒度失败 | 任务过细，任务管理时间吞掉计算收益 |
| 复制/序列化开销 | 大量中间数据传递造成明显开销 |
| 负载不均衡 | 少数慢任务决定总完成时间，其他 Worker 长时间空闲 |
| 局部加速但整体无收益 | 被修改函数变快，但项目端到端提升不足 5% |
| 端到端性能退化 | 结果正确，但候选中位时间超过串行版 1.05 倍 |
| 有效并行化 | 项目可运行、结果正确且端到端加速比至少为 1.05 |

同一次运行可以有多个次要问题，但主要统计最早使实验无法继续的阶段，避免同一失败
被多次计算。

## 8. 指标

主要指标：

- 构建/启动成功率；
- 正确率；
- 有效并行化成功率；
- 端到端加速比；
- 性能退化率；
- 各失败类型出现频率。

辅助指标：

- 修复轮数；
- 修改文件数；
- Agent调用与Token；
- 修改范围覆盖的串行热点比例；
- 局部加速与端到端加速的差距；
- 方法分析时间。

## 9. 从现象到研究问题的规则

诊断完成后，对每个候选问题按以下四项评分：

1. 是否在多个项目中重复出现；
2. 是否明显影响正确性或端到端性能；
3. 是否能通过一个明确方法改变；
4. 是否能在项目周期内完成公平对照。

最终只选择一个主要问题。必须同时写出：

- 观察现象和频率；
- 原始证据；
- 原因分析；
- 可被实验否定的研究假设；
- 一句话 insight；
- 方法与原因之间的关系；
- 支持和否定假设分别需要什么结果。

在诊断数据形成之前，本项目没有最终 insight。

## 10. 当前阶段边界

旧版 Ray、AST、正确性检查、配置搜索和调度代码只作为可复用工具。诊断阶段不会
把这些模块的数量当作贡献，也不会用旧单文件实验代替多文件项目实验。
