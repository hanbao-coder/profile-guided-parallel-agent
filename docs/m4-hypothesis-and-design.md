# M4 假设与受控实验设计

## 1. 研究问题

真实项目中的串行到并行转换，为什么在“模型已经找到了循环或批处理入口”之后仍经常失败？

M3 表明失败混合了两层因素：

1. 通用仓库编辑问题：补丁没有绑定当前源码；
2. 并行化特有问题：状态传递、结果顺序、异常语义、执行机制和开销判断不完整。

M4 的目标是把两层因素拆开，而不是继续增加互不相关的功能。

## 2. 核心观点

直接生成补丁缺少一个位于“读代码”和“写代码”之间的可验证中间层。本项目把这个中间层
定义为**并行化契约**：

- 源码锚点：入口文件、函数、行范围和内容哈希；
- 任务边界：每个 Worker 接收什么、返回什么；
- 状态边界：哪些状态只读、哪些需要合并、哪些不能跨进程；
- 语义约束：顺序、异常、退出码和公开接口行为；
- 执行选择：串行、线程或进程及其理由；
- 收益条件：样本计算时间能否覆盖启动、调度和传输开销。

契约不是模型写的一段说明，而是后续修改、验证和失败修复共同使用的结构化证据。

## 3. 可证伪假设

### H1：源码锚点假设

使用“文件 + 行范围 + 原文哈希”的编辑方式，相比让模型重写大段旧代码，能显著提高补丁
成功落盘率。

### H2：语义契约假设

在源码锚点相同的条件下，要求模型先列出状态、顺序和异常契约，能降低项目测试或固定输出
失败率。

### H3：执行与收益假设

在语义正确的候选上，加入 CPU/I/O 小样本探测和真实端到端反馈，能减少线程/进程选择错误
和并行后变慢的情况。

任何一个假设都可能被实验否定。例如 Anchor-only 若已经解决大部分错误，就说明复杂契约
没有额外价值；完整方法若仍频繁退化，就需要放弃或修改收益判断。

## 4. 方法版本

| 版本 | 源码锚点 | 语义契约 | 执行/收益反馈 |
|---|---:|---:|---:|
| B0 直接 Agent | 否 | 否 | 仅最终反馈 |
| B1 Anchor-only | 是 | 否 | 仅最终反馈 |
| B2 Anchor + Semantic Contract | 是 | 是 | 仅最终反馈 |
| B3 Full | 是 | 是 | 小样本探测 + 最终反馈 |

三项目均使用相同模型、最大轮数、测试、工作负载和输出判断。M3 的 B0 结果保持冻结，不因
后续方法效果修改基线。

## 5. 主要指标

- 补丁落盘率；
- 项目测试通过率；
- 固定端到端输出一致率；
- 有效并行成功率；
- 性能退化率；
- 有效候选加速比；
- 模型调用次数和 Token；
- 从开始到有效候选的总实验时间。

有效并行成功仍定义为：测试通过、输出一致、端到端中位加速至少 1.05 倍。

## 6. 首轮实现范围

先在 Radon 和 Chardet 上验证：

- Radon 有人工 5.98 倍上界，适合检验状态最小化和进程边界；
- Chardet 已出现“线程正确但慢”和“进程快但接口不完整”，适合检验执行选择和语义契约。

Vulture 的跨文件共享分析状态更复杂，待前两项方法稳定后作为更困难的留出项目，避免一开始
把所有失败混在一起。

## 7. 阶段终止条件

满足以下条件才进入最终扩展实验：

1. B1 在两个项目上的补丁落盘率高于 B0；
2. 至少形成一个测试和输出均正确的候选；
3. B2/B3 相对 B1 的增益能够由具体失败案例解释；
4. 全部原始响应、补丁、测试和计时均可追溯。

若 B1 不能改善落盘率，优先修正锚点协议；若 B1 改善但 B2 无贡献，不继续堆叠契约字段；
若语义正确但 B3 仍普遍变慢，则重新评估工作负载规模和收益模型。
