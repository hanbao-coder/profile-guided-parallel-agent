## 汇报摘要

### 我想解决的问题

大模型很容易把一个 Python 循环改写成 Ray 并行代码，但“能运行”不等于“更快”。任务拆得太碎、数据传得太多、各个 Worker 工作量差别太大，都会让并行版本比串行版本更慢。

### 我做了什么

我把系统分成四步：

1. 读代码，检查循环之间有没有前后依赖；
2. 让 Agent 生成并行方案；
3. 用小规模输入试跑，测任务耗时、启动开销和数据传输开销；
4. 选择 Worker 数量和 Chunk 大小，真正运行；如果结果不正确或没有收益，就回到串行版本。

### 我怎样证明它有效

我设计了三组对照：

- M0：原始串行代码；
- M1：Agent 朴素并行，直接拆成很多 Ray 任务；
- M2：加入依赖检查、试跑、任务合并、参数选择和回退的优化并行。

在 8 类真实 Ray 任务上，我进行了 3 轮独立运行，每轮每种方法正式计时 5 次，共得到 360 个正式计时样本。所有最终结果都通过正确性检查。

### 目前最重要的结果

- M1 预热后平均加速 1.740 倍，但有 37.5% 的任务比串行更慢；
- M2 预热后平均加速 2.406 倍，性能退化率降到 0%；
- M2 在 8 类任务中的 7 类胜过 M1；
- Ray 第一次启动平均需要 2.981 秒，所以第一次完整运行仍然很慢；
- 当前正式证据来自 WSL2 单台物理机器上的真实 Ray 运行，不等同于多机集群实验。

> 我认为这个项目最能体现科研能力的地方，不是代码量，而是：先提出“盲目并行可能更慢”的问题，再设置对照组，用真实运行数据找到原因，修改方法，并主动说明实验边界。

## 一、这个项目到底在做什么

假设原程序要处理 1000 张图片。串行代码是一张接一张地处理。最简单的并行做法，是把图片分给多个进程同时处理。

这里的几个词可以这样理解：

| 名称 | 大白话解释 |
|---|---|
| Agent | 会分步骤调用模型、运行代码、读取结果，再决定下一步的程序 |
| Ray | 负责把任务分给多个工作进程的 Python 工具 |
| Worker | 真正干活的进程，可以理解为“工人” |
| Chunk | 一次交给 Worker 的一包数据 |
| 加速比 | 串行时间 ÷ 并行时间；大于 1 才说明更快 |

问题在于，1000 张图片不一定应该拆成 1000 个小任务。如果每项工作很短，提交任务本身的开销就可能比计算时间还长。因此，系统必须回答三个问题：

1. 这段代码能不能安全并行？
2. 即使能并行，值不值得并行？
3. 如果值得，应该拆成多少包、用多少个 Worker？

![项目运行流程：从依赖检查、Agent 方案、小规模试跑到正确性和性能回退](assets/beginner_docs_20260801/项目运行流程.png)

## 二、为什么不能只让大模型写 Ray 代码

我最开始也以为，并行任务越多，CPU 就会越忙，程序就会越快。实际实验很快推翻了这个想法。

### 问题一：任务太碎

`tiny_tasks` 测试中，M1 创建了 2000 个 Ray 任务，预热后加速比只有 0.255，也就是比串行慢接近 4 倍。我单独测得一个空任务的固定开销约为 0.214 毫秒。M2 把很多小任务合成平均约 9.3 个大任务后，加速比提高到 3.087。

### 问题二：数据传输太大

`large_payload` 中，朴素并行的加速比只有 0.424。M2 减少任务数量和重复数据传递后，加速比达到 1.056。提升不算夸张，但至少避免了明显变慢。

### 问题三：工作量分配不均

有些输入的计算时间差别很大。平均任务时间看起来正常，但只要某个 Worker 分到了很多重任务，所有人都要等它。后来我加入了分层抽样和“慢任务惩罚”，使 `load_imbalance` 的加速比达到 2.938。

### 问题四：第一次启动很慢

Ray 启动平均需要 2.981 秒。预热后 M2 平均可以达到 2.406 倍加速，但把第一次启动也算进去，加速比只有 0.044。由此我认识到，“更快”必须说明使用场景：一次性运行和反复运行不是同一个问题。

## 三、系统是怎么搭起来的

### 项目目录

```text
profile-guided-parallel-agent/
├── benchmarks/              8 类测试程序和输入
├── configs/                 实验参数
├── src/parallel_agent/      核心代码
├── scripts/                 一键验证和正式实验脚本
├── tests/                   78 项自动检查
├── docs/data/               已冻结的正式证据
├── results/raw/             每次新实验的原始结果
└── generated/               Agent 生成的代码和日志
```

### 核心代码各自负责什么

| 模块 | 作用 |
|---|---|
| `analyzer.py` | 把代码拆成结构化信息，找循环、变量读写和明显依赖 |
| `profiler.py` | 小规模试跑，测运行时间、CPU、序列化等开销 |
| `optimizer.py` | 判断值不值得并行，选择 Worker 与 Chunk |
| `chunking.py` | 把很多小输入合成合适大小的数据包 |
| `task_fusion.py` | 把连续的小步骤放进同一个任务，减少中间传输 |
| `runner.py` | 运行 M0、M1、M2，重复计时并保存结果 |
| `agent_pipeline.py` | 管理 Agent 的分析、生成、验证和修复流程 |
| `deepseek_adapter.py` | 调用 DeepSeek，处理普通代码的语义理解和改写 |

### DeepSeek 在项目中的位置

DeepSeek 适合做“这段代码是什么意思、怎样改写”的工作，但性能参数不能完全靠模型猜。项目采用分工：

- DeepSeek：语义分析、普通代码适配、失败后的代码修复；
- 确定性程序：依赖检查、真实计时、Worker/Chunk 搜索、正确性比较和回退。

受控配对实验中，模板方案 12/12 正确；DeepSeek 方案 11/12 正确，经过 8 次修复，共使用 16,978 个生成与修复 Token。这个结果说明大模型有用，但不能代替真实运行和正确性门控。

## 四、三组对照怎样设置

![M0 原始串行、M1 朴素并行、M2 优化并行三组方法对照](assets/beginner_docs_20260801/三组方法对照.png)

### M0：原始串行

一个接一个运行。它既是时间基准，也是正确答案来源。

### M1：朴素并行

直接把循环拆成很多 Ray 任务，Worker 数和任务划分使用固定规则。它代表“只会生成并行代码”的普通方案。

### M2：优化并行

先检查依赖和副作用，再试跑；根据测量结果选择 Worker 数和 Chunk 大小，必要时合并任务。运行后与 M0 对答案。如果错误或比串行慢超过设定范围，就回退。

### 为什么这样的对照比较公平

- 三组使用相同输入和随机种子；
- 在同一台机器、同一软件环境中运行；
- 每组先预热，再重复计时；
- 比较顺序随机化，减少先后顺序的影响；
- 只有输出与 M0 一致，性能数据才算有效；
- 同时报“预热后运行”和“第一次完整运行”，不隐藏启动成本。

## 五、实验数据怎样准备

8 类任务不是随便挑的，而是分别测试不同问题。

| 任务中文名 | 主要考察点 | 朴素并行容易出现的问题 |
|---|---|---|
| 大数据传输 | 数据传递开销 | 传数据比计算还慢 |
| 负载不均 | 各任务耗时差异 | 某个 Worker 拖住全局 |
| 分形图计算 | 规则计算密集任务 | 任务切分是否合理 |
| 随机模拟 | 独立计算和归并 | 随机种子与结果合并 |
| 两两距离 | 数据块计算 | 数据块太大或太碎 |
| 素数统计 | CPU 密集任务 | Worker 和 Chunk 选择 |
| 大量小任务 | 调度固定开销 | 任务越多反而越慢 |
| 词频统计 | Map-Reduce | 文件分块与结果合并 |

正式实验设置：

- 环境：Windows 11 的 WSL2；
- 执行后端：真实 Ray 单节点运行；
- 任务数：8 类；
- 独立运行：3 轮；
- 每种方法每轮：预热 1 次，正式计时 5 次；
- 正式计时样本：8 × 3 × 3 × 5 = 360 个；
- 自动测试：78 项全部通过。

### 总体结果

| 指标 | M1 朴素并行 | M2 优化并行 |

| 任务 | M1 | M2 | 我的理解 |
|---|---:|---:|---|

| 大量小任务 | 0.255 | 3.087 | 任务合并带来最大改善 |
| 词频统计 | 1.288 | 1.508 | 合理分块后获得中等提升 |

### 第一次运行为什么还是慢

![预热后运行和第一次完整运行的加速比对比](assets/beginner_docs_20260801/冷启动与热运行.png)

预热后运行反映“系统已经启动，代码会重复执行”的场景。第一次完整运行还包含 Ray 启动成本。M2 的首次完整加速比为 0.044，说明一次性小任务不适合为了并行而启动 Ray。

我进一步计算了“需要重复多少次才能赚回 Agent 与启动成本”：中位数为 34.5 次。平均数达到 379.95 次，是因为有两类任务在预热后也几乎没有可回收的时间。这说明平均数容易被极端情况影响，所以报告中同时给出中位数和失败案例。

## 七、遇到的问题、解决过程与我的思考

### 1. “任务越多越快”是错的

最初想法：把每个数据项都变成一个 Ray 任务，可以最大化并行。

实际现象：`tiny_tasks` 创建 2000 个任务后，加速比只有 0.255。

排查方法：增加任务数量、单任务耗时和空任务开销记录，测得固定开销约 0.214 毫秒/任务。

修改：让 M2 先估计单项计算时间，把太小的任务批量打包，最终平均只提交约 9.3 个任务。

得到的认识：并行不是看“任务多不多”，而是看每个任务真正做的工作能不能盖过调度和传输成本。

### 2. 只看平均任务时间会漏掉负载不均

最初想法：平均任务时间接近，就说明分配合理。

实际现象：连续分块会把一批重任务集中交给同一个 Worker，最后所有人都等最慢的那个。

修改：对输入做分层抽样，记录任务耗时差异；当差异较大时，使用更分散的分块方法，并给“拖尾任务”增加惩罚。

得到的认识：并行总时间由最慢的 Worker 决定，平均数不能说明全部问题。

### 3. 只报告预热结果会夸大效果

最初现象：预热后 M2 平均加速 2.406 倍，看起来效果很好。

进一步检查：Ray 启动平均需要 2.981 秒，第一次完整运行反而远慢于串行。

修改：把结果拆成“第一次完整运行”和“预热后重复运行”，并计算回本次数。

得到的认识：指标必须和使用场景匹配，不能只挑好看的数字。

### 4. Windows 能运行不代表实验环境稳定

实际问题：中文用户名、较长的临时目录和 Ray 的通信路径造成不稳定；CI 中也遇到 AF_UNIX 路径长度限制。

修改：把主要 Ray 实验放到 WSL2，使用短临时路径 `/tmp/pa_ray`，同时保留 Windows 上的轻量验证。

得到的认识：运行环境不是“额外细节”，它会直接影响分布式实验能不能复现。

### 5. Agent 看错了代码对象

实际问题：普通循环先被包装成统一接口后，DeepSeek 只看到了包装层，错误地认为原函数不安全。

修改：同时保存原始源码和包装源码，用 SHA256 校验两者关系，并把二者都交给语义分析阶段。

结果：普通循环前端用 2 次模型调用、2,435 Token 得到正确输出。

得到的认识：多阶段 Agent 中，每一阶段都必须保留原始语义，不能只保证文件格式对得上。

### 6. “连上 Ray”不等于“做过多机实验”

我为实验记录了物理节点、执行节点和是否跨多个节点。当前正式实验确实使用了 Ray，但只在一台物理机器的 WSL2 中运行。

得到的认识：科研汇报要主动说清证据边界。单机多进程结果可以证明方法原型，但不能冒充多机通信结果。

## 九、目前局限与下一步

### 当前局限

- 正式 Ray 数据来自单台物理机器，还没有真实多机网络通信证据；
- 当前支持单文件或少量函数，不能处理任意大型 GitHub 仓库；
- 依赖分析能识别常见情况，但不是完整编译器；
- DeepSeek 配对实验只有 12 组，样本量仍较小；
- DAG 调度结果目前主要是确定性模型验证，不能当作真实 Ray 性能结论；
- 第一次启动成本很高，项目更适合重复执行的任务。

### 下一步优先级

1. 在两台机器上补真实 Ray 集群实验，记录网络传输量；
2. 增加更多带共享状态和多阶段依赖的程序；
3. 把静态依赖信息和动态试跑信息结合得更紧；
4. 为 DeepSeek 增加更多普通 Python 循环的受控测试；
5. 尝试接入导师团队的任务执行框架，与 Ray 结果对比。

## 十一、老师可能追问的简短回答

### Q1：你的创新点是什么？

不是“大模型能写 Ray 代码”，而是把依赖检查、真实试跑、任务粒度选择、通信开销权衡和性能回退放进同一个闭环，重点降低盲目并行造成的性能退化。

### Q2：为什么选 Ray，不选 MPI？

项目时间短、目标语言是 Python。Ray 更容易把普通函数变成任务，也能从单机扩展到集群，适合先验证方法。MPI 更底层，但开发和调试成本更高。

### Q3：怎样保证并行结果没有算错？

M0 产生黄金结果，M1 和 M2 都必须与它比较。整数和结构化数据做精确比较，浮点数允许极小误差。错误候选不会进入性能结论。

### Q4：为什么 M2 不是每个任务都大幅领先？

有些任务本来就不适合并行，例如数据传输占比高。M2 的目标包括“知道什么时候不要冒险”，所以有时只做到接近串行或回退，而不是强行追求高加速。

### Q5：这是多机分布式实验吗？

不是。当前是 WSL2 单台物理机器上的真实 Ray 运行，验证了任务并行、调度开销和粒度策略。多机网络通信需要下一阶段补实验。

### Q6：你主要用 AI 开发，怎样证明自己理解了？

我能用自己的话解释数据怎样从输入分到 Worker、结果怎样合并、为什么小任务会变慢、为什么要区分冷启动和预热、三组对照怎样保证公平，并能独立运行复现实验和解释失败案例。

### Q7：最重要的实验发现是什么？

“是否并行”和“怎样分块”比“是否生成了并行代码”更重要。最典型的是大量小任务：朴素并行只有 0.255 倍，合并后达到 3.087 倍。

### Q8：如果继续一个月，最先做什么？

先做两台机器的真实 Ray 集群实验，因为当前最大的证据缺口是网络通信；然后扩大普通 Python 循环和复杂依赖测试集。

## 十二、结论

本项目已经完成一个可运行、可验证、可复现的自动并行化 Agent 原型。结果表明，简单拆分任务虽然容易实现，却会在小任务、大数据传输和负载不均时产生明显性能退化。加入依赖检查、性能试跑、自适应任务粒度和回退后，M2 在 8 类任务上取得 2.406 倍的预热后平均加速，并把性能退化率从 37.5% 降到 0%。

更重要的是，我通过失败案例认识到：科研不是只展示最好结果，而是把问题说清楚、把对照做公平、把数字测真实、把边界讲明白，再根据证据修改方法。
