# 真实项目实验设计与结果

## 1. 研究对象

| 项目 | 固定版本 | 串行工作负载 | 主要并行风险 |
|---|---|---|---|
| Radon | 6.0.1 | 批量分析 Python 源文件并汇总结果 | 分析器状态、结果排序、进程传参 |
| Vulture | 2.16 | 扫描项目并找出未使用代码 | 跨文件共享分析状态、定义和使用关系 |
| Chardet | 7.0.0.dev0 | 对一批真实字节文件做编码检测 | 输入批处理、结果顺序、进程启动成本 |
| MkDocs | 1.6.1 | 构建项目官方完整文档站点 | 插件状态、当前页面状态、输出顺序和链接 |

Pygments 2.20.0 也经过筛选，但没有纳入：它的官方命令行入口一次只处理一个文件，批量循环
只能写在项目外的实验适配器中。若让 Agent 改这个外部循环，就不能代表“修改真实项目”。

## 2. 对照组

- **B0 原始串行项目**：每次 Agent 试验开始前重新运行项目测试、固定输出和串行计时；候选性能
  与同次试验的串行基线配对比较，不把单独某次机器计时当作所有试验的共同常数。
- **B1 普通 Agent**：相同 DeepSeek 模型、工具和轮数，不提供本项目的源码锚点、语义契约、
  稳健性能反馈与回退策略。
- **B2 完整方法**：源码来源预检、锚点、语义契约、项目测试、固定输出、稳健性能反馈和回退。
- **A1 只加语义约束**：用于 MkDocs 消融；提供源码锚点和并行化契约，但不提供候选性能反馈
  与自动回退。
- **B3 人工参考版本**：在 Radon 上由人工选择最小任务状态，用来检查“避开 Worker 状态传递
  后是否存在端到端收益”。B3 只覆盖一个项目，因此不进入四项目平均成功率，也不能自动视为
  性能上界。

所有 Agent 组都使用 DeepSeek V4 Pro 处理仓库分析和修改，不复用前一次运行的补丁或回答。

## 3. 有效结果判定

一项修改必须同时满足：

1. 原项目测试通过；
2. 固定端到端输出哈希与串行版本一致；
3. 修改中存在实际的线程或进程并行结构；
4. 串行和候选配对测量后，端到端中位加速至少为 1.05 倍。

只让某个内部函数变快、只通过少量新增测试，或只出现并行库名称，都不算有效并行化。

## 4. 主实验结果

| 方法 | 运行数 | 有效并行 | 安全回退 | 错误修改 | 未形成方案 |
|---|---:|---:|---:|---:|---:|
| B1 普通 Agent | 12 | 0 | 0 | 6 | 6 |
| B2 完整方法 | 12 | 1 | 10 | 0 | 1 |

完整方法唯一一次有效并行出现在 Chardet，端到端加速为 3.251 倍。这个结果说明方法能够找到
一个真实有效候选，但 1/12 的成功率也表明，不能把该结果推广为“多数项目都能自动加速”。

## 5. 分项目结果

| 项目 | B1 普通 Agent（3 次） | B2 完整方法（3 次） |
|---|---|---|
| Chardet | 3 次错误修改 | 1 次有效并行，2 次安全回退 |
| MkDocs | 2 次错误修改，1 次未形成方案 | 3 次安全回退 |
| Radon | 3 次未形成方案 | 3 次安全回退 |
| Vulture | 1 次错误修改，2 次未形成方案 | 2 次安全回退，1 次未形成方案 |

## 6. MkDocs 消融

| 方法 | 错误修改 | 安全回退 | 未形成方案 |
|---|---:|---:|---:|
| B1 普通 Agent | 2 | 0 | 1 |
| A1 只加语义约束 | 2 | 0 | 1 |
| B2 完整方法 | 0 | 3 | 0 |

每组只有 3 次，因此这是机制检查，不是大样本统计。它支持的有限结论是：对于 MkDocs，单靠
事先写出的语义约束没有阻止错误修改；加入真实验证和回退后，三个不合格候选都没有进入最终
代码。

## 7. Radon 人工参考复核

早期记录曾把 Radon 的人工参考版本作为约 5.98 倍的性能上界。为了避免在旧计时结果上继续
建立新假设，本轮用固定源码、干净副本、路径无关输出协议和相同输入重新运行 B0/B3：

| 版本 | 中位耗时 | 相对串行加速 | 测试和输出 |
|---|---:|---:|---|
| B0 原始串行 | 12.7008 秒 | 1.0000 倍 | 通过 |
| B3 人工参考 | 12.7182 秒 | 0.9986 倍 | 通过 |

![Radon 人工参考固定协议复核](figures/radon-manual-reference-recheck.png)

两版输出哈希完全相同，但 B3 没有达到 1.05 倍有效门槛。旧的 5.98 倍结论因此撤回。这个结果
说明“减少跨进程状态”能修复一类正确性问题，却不等于整个项目一定会变快。机器可读结果见
`docs/data/radon-manual-reference-summary.json`。

## 8. 实验中的协议修正

实验过程中发现两个会让结论失真的问题，并保留了排除记录：

1. Chardet 使用 `src` 目录布局，早期运行实际导入了环境中已安装的原版本，而不是候选源码。
   修正为运行前检查模块来源，旧数据全部排除并重跑。
2. MkDocs 的 API 文档解析依赖当前工作目录。第一次基线从错误目录启动，生成站点哈希不同。
   该次运行标记为排除，之后固定从项目根目录启动并重跑。

这两项不属于 Agent 方法效果，但它们说明真实仓库实验必须证明“测到的确实是刚修改的源码”。

## 9. 生成紧凑结果和图表

在仓库根目录运行：

```powershell
.\.venv\python.exe scripts\summarize_m6_study.py
```

脚本从本机原始实验目录读取结果，重新生成 `docs/data/m6-study-summary.*` 和三张中文图。若原始
目录不存在，可直接查看仓库中已经提交的紧凑结果；但不能声称重新执行了 Agent 实验。

## 10. 原始证据完整性

正式统计包含 27 次 Agent 运行：B1 12 次、B2 12 次、A1 3 次。每次必须存在导入预检、
最终结果、提示、原始回复、事件日志、补丁和串行基线验证。运行：

```powershell
.\.venv\python.exe scripts\audit_research_evidence.py
```

本次审计结果为 27/27 完整，并额外记录 41 份排除说明。每个原始文件的大小和 SHA-256 位于
`docs/data/research-evidence-manifest.json`。清单只能证明本机哪些文件接受过审计；若删除本机
`results/`，清单不能还原模型原始回复。
