# Agent 驱动项目级并行化：相关工作与研究问题形成方案

## 1. 文档目的

本项目最初实现了 Python 循环分析、Ray 代码生成、正确性验证、任务粒度搜索和
性能回退。现阶段不再把“增加更多功能”作为主线，而是研究以下过程：

1. 让同一个 Agent 尝试并行化一组可运行的串行项目；
2. 使用编译/启动、测试和性能数据记录它实际遇到的问题；
3. 对失败进行分类和统计；
4. 从反复出现、影响较大的问题中提出一个可检验的观点；
5. 针对该问题设计方法，并与未改进的 Agent 做对照实验。

当前主题仍然是“使用 Agent 将串行代码或项目并行化”，但研究对象从单个规范化
Python 文件扩展到带有多文件依赖、测试和运行入口的小型项目。

## 2. 相关工作

### 2.1 LLM 生成并行代码

Nichols 等人在 HPDC 2024 提出 ParEval。该基准包含 420 个科学计算与并行编程
任务，覆盖 12 类问题和多种执行模型，并同时评价生成代码的正确性、加速和扩展
效率。这项工作说明，并行代码不能只用“是否生成成功”评价，还必须实际运行并测量
性能。

ParEval 主要以独立编程问题为单位。它为本项目提供了正确率、加速比和并行效率等
评价方式，但不能直接回答 Agent 在完整项目中如何选择修改位置、理解跨文件依赖和
维护构建入口。

### 2.2 仓库级并行代码转换

Davis 等人在 2025 年提出 ParEval-Repo，用于评价 LLM 对完整 HPC 代码库进行
GPGPU 执行模型转换的能力。论文同时比较非 Agent 方法和自顶向下 Agent 方法，
评价能否构建、功能是否正确、构建错误类别和推理 Token 成本。论文发现，小程序的
转换具有可行性，但当仓库扩大后，构建系统和跨文件依赖会成为明显困难。

这项工作与本项目最接近。它说明从单文件扩展到项目级以后，问题不只是生成某段
并行代码，还包括：

- 找到正确的修改范围；
- 理解调用关系和跨文件数据依赖；
- 保持原有构建、配置和测试入口；
- 避免局部代码正确但整个项目无法运行。

ParEval-Repo 主要关注不同 GPGPU 编程模型之间的代码库翻译。本项目计划研究的
重点是：Agent 面对串行项目时，如何发现有收益的并行化位置，并利用真实执行证据
避免错误或无收益的修改。

### 2.3 仓库级代码 Agent 与上下文

CodeAgent 将代码检索、实现和测试工具接入 Agent，用于仓库级代码生成。它说明
Agent 在完整仓库中需要主动查找相关文件、调用工具并根据执行结果修复，而不能只靠
一次提示词生成。

RepoExec 进一步研究仓库上下文对代码生成的影响，评价可执行性、功能正确性和
依赖利用。结果说明，依赖上下文不完整会影响模型判断，而只给较小上下文可能得到
具有误导性的结果。

这些工作对本项目的启发是：项目级并行化不能把整个仓库不加选择地塞进提示词，
也不能只给 Agent 一个热点函数。需要确定与候选修改相关的调用链、测试、输入输出
和依赖文件。

### 2.4 执行反馈与性能优化

PerfCodeGen 使用单元测试保证功能正确，再把实际运行时间和最慢测试反馈给模型，
让模型继续修改正确代码。它表明，执行反馈可以帮助 LLM 生成更高效的代码，而且
性能优化不能由模型自己评价。

PerfCodeGen 面向通用 Python 编程题，不专门研究并行化，也不处理仓库级修改。
本项目可以借鉴它的“正确性门控—性能测量—反馈修改”流程，但需要额外解决并行化
位置选择、依赖安全、任务粒度和跨文件集成问题。

### 2.5 传统自动并行化

Tournavitis 等人的 profile-driven auto-parallelization 工作指出，单纯依赖静态
分析难以发现和选择复杂程序中的有效并行机会，因此将运行剖析用于并行区域发现，
并根据目标机器选择映射方案。

AutoTornado 则结合静态依赖和纯函数分析，判断 Java 循环是否能够安全并行，并在
运行时使用这些结果。它说明，依赖安全和运行收益是两个不同问题：一个循环没有明显
依赖，并不代表并行后一定更快。

这些传统方法不使用 LLM Agent，但为项目提供了两个重要原则：

1. 先判断语义和依赖是否允许并行；
2. 再用实际运行信息判断是否值得并行。

### 2.6 Ray 执行后端

Ray 提供 Task、Actor、分布式调度和对象存储等抽象，可以在单节点和多节点上运行
相同的任务代码。本项目继续使用 Ray 作为候选并行项目的执行后端，但研究对象是
Agent 的分析和修改策略，不修改 Ray 内部调度器。

## 3. 当前相关工作的空缺

已有工作分别覆盖了并行代码生成、仓库级代码 Agent、执行反馈和传统自动并行化，
但本项目目前还没有证据回答以下问题：

> 当 Agent 从“修改一个独立函数”扩展到“并行化一个可运行项目”时，最常见且最
> 影响最终效果的问题究竟是什么？

可能的问题包括：

1. 项目无法安装、构建或启动；
2. Agent 找错热点，修改了对总时间影响很小的函数；
3. 跨文件依赖或共享状态判断错误；
4. 测试通过，但结果语义或输出顺序发生变化；
5. 任务划分过细，调度和数据传输开销超过收益；
6. 局部函数加速，但项目端到端时间没有改善；
7. 修改无法与原有配置、命令行或测试入口集成。

在完成诊断实验之前，不能预先宣称其中某一项一定是主要问题。下一阶段首先要用
统一协议收集证据，再决定最终研究问题。

## 4. 项目级诊断实验

### 4.1 项目选择原则

第一阶段选择 6 个小型串行项目，每个项目满足：

- 至少包含 3 个源代码文件，而不是单个脚本；
- 有明确安装方式和固定运行入口；
- 有自动测试或可比较的黄金输出；
- 串行运行时间足够长，能够测量性能差异；
- 包含可解释的 CPU 密集或批处理部分；
- 许可证允许科研使用；
- 在固定输入上能够重复运行。

项目类型覆盖科学计算、图像/文本批处理、数据分析、图算法和多阶段流水线。先筛选
项目，不为了数量选择无法稳定复现的大型仓库。

### 4.2 固定 Agent 协议

每个项目使用同一个模型、提示词、Token 上限、工具权限和最大修复轮数。Agent
依次执行：

1. 阅读 README、运行入口和测试；
2. 运行串行项目并采集性能剖析；
3. 给出并行化计划和计划依据；
4. 修改项目并生成补丁；
5. 安装或构建候选版本；
6. 运行原有测试和输出一致性检查；
7. 测量端到端时间；
8. 根据错误或性能结果进行有限轮修复。

每个项目独立运行 3 次，保留每次计划、补丁、测试日志、运行时间、Token 和失败
原因，不只保留最后一次成功结果。

### 4.3 失败分类

每次运行按照最早阻断阶段和最终结果记录：

| 类别 | 判断条件 |
|---|---|
| 环境/构建失败 | 无法安装、导入或启动 |
| 定位失败 | 修改位置不是主要热点，端到端时间几乎不变 |
| 依赖失败 | 跨文件调用、共享状态或数据依赖处理错误 |
| 正确性失败 | 测试或黄金输出不一致 |
| 集成失败 | 并行代码无法接入原有入口和配置 |
| 性能失败 | 正确但比串行慢 5% 以上 |
| 有效并行化 | 正确且端到端时间至少改善 5% |

同一次运行可以记录多个次要问题，但主要统计“最早阻断阶段”，避免一项失败被重复
计数。

## 5. 研究问题如何从实验中形成

完成首轮诊断后，根据“出现频率、性能影响、是否能在剩余时间解决”选择一个问题。

例如，如果结果表明多数正确候选没有端到端收益，而且 Agent 经常修改非热点函数，
可以形成以下研究问题：

> 运行剖析和依赖切片能否帮助 Agent 在项目中选择更有收益的并行化边界？

对应的项目观点可以是：

> 项目级自动并行化的首要问题不是怎样生成并行语法，而是怎样选择一个既占主要
> 运行时间、又能安全独立执行的修改边界。

方法可以只包含一个核心变化：向 Agent 提供“热点调用链、相关文件、测试入口和
输入输出规模”组成的证据包，而不是提供整个仓库或单个孤立函数。

对照组为：

1. Whole-Repo Agent：只阅读仓库和文字任务；
2. Static-Context Agent：增加静态调用和依赖上下文；
3. Profile-Guided Agent：增加真实热点、调用次数和输入规模；
4. Oracle Boundary：人工给出正确修改范围，作为上界。

如果诊断实验发现跨文件依赖才是最主要问题，则研究问题应相应调整为“依赖切片
如何改善项目级并行化正确率”，而不是强行保留热点定位结论。

## 6. 评价指标

主要指标：

- 项目可构建率；
- 测试/黄金输出通过率；
- 有效并行化成功率；
- 项目端到端加速比；
- 性能退化率。

辅助指标：

- Agent 修复轮数；
- 修改文件数量；
- 上下文 Token；
- 计划与真实热点的重合程度；
- 并行化边界涉及的跨文件依赖数量。

最终报告需要按项目和失败类别展示原始结果，不能只报告平均加速比。

## 7. 当前最合理的研究定位

在诊断实验完成前，项目暂定为：

> 面向项目级串行程序的执行证据驱动并行化 Agent：一项关于并行化失败模式与
> 修改边界选择的实证研究。

该定位包含两个阶段：

1. 实证阶段：发现 Agent 并行化完整项目时的主要失败模式；
2. 方法阶段：针对其中一个主要问题提出并验证改进。

现有 Python/Ray 原型负责执行、验证和记录，不再作为主要贡献本身。
