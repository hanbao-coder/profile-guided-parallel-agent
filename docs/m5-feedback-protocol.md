# M5 正确性门控与性能反馈协议

## 1. 方法动机

M4 的语义契约实验中，6 个候选有 4 个保持了完整语义，但没有一个达到
1.05× 的端到端加速。其中既有几乎持平的候选，也有慢于串行的候选。这说明：

> 修改前的语义分析能降低改错概率，但 Agent 仍需要看到修改后的真实运行结果，
> 才能判断当前并行位置、后端和任务边界是否值得保留。

M5 因此只增加一个核心机制：把每一轮候选的正确性与端到端性能按固定顺序反馈
给 Agent，并要求它基于反馈修复或安全回退。

## 2. 每轮验收顺序

每次 Agent 修改代码后，系统自动执行：

1. 运行项目正确性测试；
2. 测试通过后，运行固定的端到端工作负载；
3. 检查多次输出是否稳定，并与串行基线哈希比较；
4. 只有输出一致时才计算端到端加速比；
5. 把失败类型、串行时间、候选时间、加速比和目标阈值返回给 Agent。

候选必须同时满足以下三个条件才可接受：

- 项目测试通过；
- 端到端输出与串行基线一致；
- 加速比不低于预先固定的 1.05×。

如果候选不满足条件，Agent 不能直接结束。第一次失败后必须至少进行一轮有反馈
依据的修正。如果轮数用完或 Agent 判断没有安全方案，系统恢复实验开始前的串行
源码，避免把错误或更慢的代码作为最终结果。

## 3. 与 M4 的区别

| 阶段 | 修改前约束 | 修改后反馈 | 不合格候选处理 |
|---|---|---|---|
| M4-B2 | 源码锚点 + 语义契约 | Agent 自己选择测试或计时 | 可能直接结束 |
| M5 | 同上 | 每次修改后自动执行正确性和性能门控 | 必须修正，最终可安全回退 |

M5 没有加入项目专用答案，也没有告诉 Agent 应修改哪个函数。Agent 仍使用相同的
源码读取、搜索和修改权限；新增信息只来自当前候选的真实执行结果。

## 4. 协议校准及排除记录

正式实验前进行了协议校准，所有目录均保留，但不进入正式统计。

### 4.1 Chardet 校准

- 第一次校准：Agent 在首个慢候选后立即回退，没有使用反馈修正。
  处理：要求第一次失败后至少修改一次。
- 第二次校准：修改后源码哈希失效，Agent 重复读取同一文件并耗尽轮数。
  处理：每次修改结果自动返回当前代码片段及新哈希。
- 第三次校准：Agent 完成两轮候选，速度分别约为 0.868× 和 0.739×，随后安全
  回退，说明“修改—验证—反馈—再修改—回退”已经贯通。

### 4.2 Radon 校准

- 第一次校准：Agent 定位到新的依赖文件后连续读取同一片段，没有发出修复。
  处理：一次有针对性的修复读取之后，下一步只能修改或回退；当前有效哈希以紧凑
  列表单独保存在 Agent 工作记忆中。
- 第二次校准：Agent 连续生成 3 轮候选，每轮均由完整测试判为错误，轮数结束后
  自动恢复串行源码；最终仓库没有残留补丁，原测试通过。

这些改变只修正 Agent 与编辑工具之间的交互，不改变正确性标准、性能工作负载、
加速阈值或项目源码答案。

## 5. Chardet 正确性测试调整

正式 M5 实验固定排除两项与候选语义无关的环境测试：

1. `test_symlink_used_as_is`：普通 Windows 用户没有创建符号链接的权限；
2. `test_ratio_cold_vs_warm_model_loading`：比较极短函数的冷/热启动时间比例，
   在机器负载变化时，未修改的原始项目也可能超过阈值。

排除后在未修改的固定版本上复核结果为：9324 项通过、8 项按条件排除、21 项为
项目标记的预期失败。项目功能正确性和我们的独立端到端性能工作负载均继续保留。

## 6. 正式实验规则

- 每个项目从固定 commit 的干净副本开始；
- 每个项目 3 次独立 Agent 运行；
- 不从校准结果中挑选代码或提示给正式运行；
- 保留每轮模型回答、动作、源码补丁、自动测试、快速性能反馈和最终正式性能结果；
- 正确候选的正式性能结果仍采用预热 1 次、重复 5 次的中位数；
- 校准目录与正式目录分开，汇总脚本只读取正式目录。
