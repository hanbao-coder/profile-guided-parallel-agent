# 受控 LLM 并行代码生成：v0.4 设计与预检

日期：2026-07-29

## 1. 为什么增加这一版本

此前系统中的 DeepSeek 已经负责语义分析和并行方案规划，但候选程序的主体由
确定性模板生成。这个设计适合建立可靠基线，却不足以证明 Agent 能够重构代码。

v0.4 让 DeepSeek V4 Pro 真正生成并行实现，同时保留一个可信脚手架负责命令行、
源程序加载、输出规范化和结果记录。这样既扩大模型的决策空间，又不允许模型任意
修改整个执行环境。

## 2. 受控生成契约

模型只能生成两个函数：

```python
def partition_items(items, chunk_count):
    ...

def execute_parallel(source_path, items, workers, chunks):
    ...
```

候选实现必须使用 `ProcessPoolExecutor` 和项目提供的 `_safe_run_chunk`。模型不能
生成导入语句、顶层执行语句、类、异步代码、文件写入、网络访问、系统命令、
`eval`、`exec`、`open` 或动态函数调用。

执行顺序为：

```text
DeepSeek 生成实现
→ Python AST 语法与允许列表检查
→ 拼入可信脚手架
→ 独立子进程运行
→ 与串行黄金输出比较
→ 失败时把结构化错误反馈给 DeepSeek
→ 超过修复次数则拒绝候选
```

安全检查是缩小风险面的工程门控，不等价于操作系统级强沙箱。正式处理不可信
第三方代码时仍应放入隔离容器或虚拟机。

## 3. 真实安全拦截与修复案例

在 Prime Count 手工预检中，模型第一版实现使用了不在允许列表中的
`divmod`。系统在执行前将其拒绝，并返回：

```text
generated_code_safety_error:
Call is not allowlisted: divmod
```

DeepSeek 根据该反馈重新生成实现；第二版通过 AST 安全门、成功运行，并与串行
程序得到相同结果 `1767`。该案例使用 1 次代码修复，证明代码级反馈确实作用于
模型生成的实现，而不是仅修改结构化计划。

## 4. 四任务功能预检

预检任务为 Prime Count、Tiny Tasks、Word Count 和 Pairwise Distance。每组仅
运行 1 次，因此本节只用于验证功能与成本，不能作为正式性能结论。

| 生成方式 | 正确作业 | 失败作业 | 模型调用 | Token | 费用上界 |
|---|---:|---:|---:|---:|---:|
| 确定性模板 | 4/4 | 0 | 8 | 7,762 | $0.00451 |
| 受控 LLM 代码生成 | 4/4 | 0 | 15 | 22,832 | $0.01553 |

四个 LLM 候选均通过安全检查并得到正确输出。LLM 组调用和 Token 较高，原因包括
额外代码生成阶段，以及初次预检时部分 Pro 响应未在输出预算内返回合法 JSON。
随后将代码生成与代码修复阶段改为 V4 Pro 非思考模式；恢复执行的两个任务均在
一次代码生成调用内返回合法实现。

单次计时下，模板和 LLM 组的宏平均端到端加速分别约为 0.744 倍和 0.647 倍。
由于每个候选只测量一次、模型分析调用也不是配对复用，这一差异不能用于判断哪种
生成器性能更好。正式比较必须至少进行 3 次独立生成，且每个候选进行预热和
3～5 次随机顺序测量。

## 5. 当前能得出的结论

1. DeepSeek 已不再只输出分析 JSON，而是真正生成可运行的并行实现；
2. 受控 AST 门可以在执行前拒绝不符合契约的代码；
3. 安全错误可以触发代码级修复并得到正确候选；
4. 与模板相比，自由代码生成明显增加模型成本；
5. 当前数据只能证明工程可行性，不能证明自由生成带来性能收益。

## 6. 下一步正式实验

- 四个任务各进行 3 次独立模型生成；
- 每个候选预热 1 次、正式计时 3 次并随机化串并行顺序；
- 比较模板与 LLM 的生成成功率、代码修复率、安全拒绝率、端到端加速和 Token；
- 对 LLM 生成组继续加入性能反馈，检验其是否能改变分块策略并减少性能退化；
- 保留模板作为低成本、低方差的工程基线。
