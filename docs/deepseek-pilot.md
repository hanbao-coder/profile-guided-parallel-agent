# DeepSeek 在线 Agent 首次验证

验证日期：2026-07-29

## 目的

确认真实大模型可以接入当前的结构化分析—规划—生成—执行闭环，同时验证：

- API 配置有效；
- 模型产物能通过本地 Schema 与安全 Gate；
- 自动生成候选程序能被独立子进程执行；
- 串行与并行结果一致；
- 日志不会泄露 API Key。

## 设置

- 模型：`deepseek-v4-flash`
- 输入：Prime Count、Prefix Sum、Tiny Tasks
- 输入规模：仅用于功能验证的小规模输入
- 最大 Worker：2
- Chunk：2
- 最大修复轮数：1

## 结果

| 项目 | 结果 |
|---|---|
| Agent 状态 | accepted |
| 有完整日志的 DeepSeek 调用数 | 5 |
| 有完整日志的总 Token | 4,556 |
| Prime Count | accepted，串行/并行输出均为 1,767 |
| Prefix Sum | rejected，静态 Gate 检出跨迭代依赖 |
| Tiny Tasks | accepted，串行/并行输出均为 710,087,060 |
| 实际修复轮数 | 三个案例均为 0 |
| 生成产物中的 Key 匹配数 | 0 |

这次小规模验证只用于检查端到端功能，不用于形成正式性能结论。不过 Tiny
Tasks 清楚暴露了一个方向性事实：候选代码虽然正确，端到端并行执行约
0.173 秒，串行约 0.083 秒。后续的性能 Agent 必须读取实测时间，并拒绝或
回退这种“正确但更慢”的方案。

## 发现并修复的问题

第一次真实响应返回了合法 JSON，但 `rationale` 是空数组。JSON 语法正确不等于
符合研究产物约束，因此原系统在 `AnalysisArtifact.validate()` 阶段拒绝了结果。

处理方式：

1. 继续由 AST 和函数契约决定结构事实；
2. 当模型建议并行但理由为空时，加入明确的确定性说明；
3. 非列表类型的 hazards 不再直接进入集合运算；
4. 新增回归测试，确保相同响应不会再次中断流水线。

这次失败可以作为报告中的真实 Agent 可靠性案例：模型输出必须同时经过语法、
Schema、静态安全和运行正确性四层门控，不能只检查“是不是 JSON”。

另一个失败来自静态分析：初版把 `unit()` 内部局部累加变量误认为不同
`unit(item)` 调用之间的共享依赖，导致 Tiny Tasks 被错误拒绝。修复后，完整
函数契约允许任务内部存在局部串行循环，但全局共享状态仍被拦截，并且候选
程序仍必须通过串并行结果一致性检查。

## 尚不能得出的结论

- 不能由一次调用推断 DeepSeek 的平均正确率；
- 不能把本次小规模运行时间作为性能数据；
- 不能说明模型对任意 Python 程序都能完成并行化；
- 还需要安全反例、细粒度反例和多次独立运行。
